# 보안 모델

> 무엇을 막고, 무엇을 막지 못하며, 무엇이 깨지면 제품이 무너지는가.

## 위협 주체와 대응

| 공격 | 무엇을 노리는가 | 대응 | 강도 |
|---|---|---|---|
| 사후 서사 | 결과를 본 뒤 판단을 소급 기록 | `windowStart >= 커밋 시각` (I4) | **컨트랙트 강제** |
| 거짓 정산 | 관측값과 모순되는 결과 기록 | 컨트랙트가 `result` 재계산·대조 (I17) | **컨트랙트 강제** |
| 기준 바꾸기 | 나중에 유리하게 지표 정의 변경 | 문서 바이트 해시가 온체인, 등록 즉시 `frozen` | **컨트랙트 강제** |
| 관측 시점 고르기 | 유리한 순간의 값을 제출 | `observedAt == windowEnd` (I8) | **컨트랙트 강제** |
| 복사 공격 (CT18) | 남의 commitment를 자기 것으로 | 프리이미지에 attester 포함 | **검증 단계** — 아래 참조 |

| 거짓 관측값 | 사실과 다른 값을 제출 | 제3자 재현 + 이의 | **약함 — Phase 2 오라클** |

### 복사 공격 차단이 걸리는 자리

**컨트랙트는 프리이미지를 재계산하지 않습니다.** `decisionCommitment != 0` 만 검사하므로
(I1), B가 A의 commitment를 그대로 복사해 커밋하는 것 자체는 **온체인에서 성공합니다.**

차단은 **검증 단계**에서 일어납니다. 프리이미지에 attester가 들어 있으므로,
A의 `(salt, payload)`로 대조하면 B의 주소로 계산되어 불일치가 납니다.

```
온체인   B 의 복사 커밋 → 성공 (컨트랙트는 막지 않는다)
검증     A 의 salt·payload 로 대조 → 불일치 (검증기가 attester 를 온체인에서 읽는다)
```

**검증 도구가 attester를 입력받지 않는 것이 핵심입니다.** 입력받게 만들면 공격자가
원래 attester를 타이핑해 거짓 일치를 만들 수 있습니다. 그래서 화면도 CLI도
attester를 읽기 전용으로 다룹니다.

## 신뢰 가정

이것들이 깨지면 POI의 주장도 함께 무너집니다.

1. **keccak256 충돌 저항성** — commitment 구속의 전제
2. EAS 프리디플로이가 정직하게 동작 — 우리 리졸버를 실제로 호출한다
   *(포크 테스트가 실제 바이트코드 상대로 이를 확인한다)*
3. 체인 시각이 조작되지 않음 — 모든 시점 불변식이 `block.timestamp` 기반
4. 업비트 공개 API가 과거 데이터를 바꾸지 않음 — 재현의 전제
5. RPC 노드가 정직하게 응답 — 조회 결과의 전제
6. 도장 스키마·발급자가 정직하게 검증 — 「검증 지갑」 표시의 전제.
   컨트랙트는 스키마 UID와 발급자 주소가 맞는지만 확인할 뿐,
   도장이 KYC를 제대로 했는지는 알 수 없습니다 *(I18)*

## 사용자 측 위험

| | |
|---|---|
| salt 유실 | 공개(Reveal)가 **영구 불가**해집니다. 커밋은 남지만 내용을 증명할 수 없습니다. 그래서 발행 전에 salt 백업 확인을 강제합니다 |
| 키 유실 | 그 지갑의 결정에 결과를 등록할 수 없습니다 → 전부 「기한초과」가 됩니다 |
| 잘못된 지표 선택 | 등록 후 `frozen`이라 결정 자체를 새로 커밋해야 합니다 |

## 운영 측 위험 — 지금 열려 있는 것

**`POIDecisionResolver`의 owner는 2-of-2 Safe입니다** (`0x215253B8…DCE1`, 2026-07-30 이전 완료).
배포 지갑 단독으로는 아무것도 못 합니다.

owner가 할 수 있는 것 셋:

| | 무엇 | 제한 |
|---|---|---|
| `addMetric` | 새 지표 등록 | **이미 등록된 지표는 `frozen`이라 못 바꿉니다** |
| `setVerifiedAddressSchema` | 도장 스키마 변경 | 변경이 `VerifiedAddressSchemaChanged` 이벤트로 드러납니다 |
| `setIssuer` | 허용 발급자 추가·제거 | 변경이 `IssuerChanged` 이벤트로 드러납니다 |
| `sealRegistry` | 지표 추가 영구 봉인 | 되돌릴 수 없습니다 |

**과거 기록은 안전하고 미래 등록만 신뢰가 필요합니다** — 발행된 결정·정산은 owner도
바꿀 수 없고, 등록된 지표의 `definitionHash`도 동결돼 있습니다.

`sealRegistry()`는 넣었지만 **호출하지 않았습니다** — Phase 1에서 지표를 더 등록해야
하기 때문입니다. `renounce`도 같은 이유로 하지 않습니다.

> **두 키를 같은 사람이 보유합니다.** 단일 키 탈취 위험은 사라졌지만
> 권한이 여러 주체로 분산된 것은 아닙니다. 1인 팀이라는 사실은 그대로입니다.

나머지 세 리졸버(note·settlement·challenge)의 owner는 **아무 권한이 없습니다** —
`initialize`가 일회성이고 다른 `onlyOwner` 함수가 없습니다.

## 조회 완전성

**조회된 것이 전부라는 보장이 없습니다.** RPC 인덱싱 범위와 노드 상태에 따라
목록이 달라질 수 있습니다. 그래서 모든 목록에 그 사실을 표시하고 **건수를 세지 않습니다.**

건수를 세는 순간 "조회된 것이 전부"라는 거짓 전제가 들어갑니다.
