# 월렛 탑재 가능성

> **탑재는 아직 검증되지 않았습니다.** 실제 GIWA 월렛 안에서 동작하는지 확인한 적이 없습니다.
> 아래는 「담길 수 있다」가 아니라 **「왜 여기에 있어야 하는가」** 를 적은 것입니다.

## 왜 지갑인가 — 판단의 재료가 이미 지갑에 있다

POI 의 결정은 **술어(predicate)** 입니다.

```
metricId · op · threshold        예) BTC_PRICE_KRW_AT_END > 89,291,000
```

「무엇을, 어떤 조건으로 본다」는 문장이고, 결과가 나온 뒤 **컨트랙트가 산술로 판정**합니다.

그런데 판단에는 재료가 있습니다 — **누가 말했는가**, 그리고 **그때 실제로 무엇을 들고 있었는가**.
이 둘이 지갑 안에 있습니다. 밖에서는 가져올 수 없습니다.

| 재료 | 어디에 있나 | 지금 상태 |
|---|---|---|
| 누가 말했는가 | 도장 **Verified Address** | **연동 완료** — 컨트랙트가 스키마·발급자를 검증한다 |
| 무엇을 들고 있었는가 | 도장 **Verified Balance** | 스키마가 온체인에 있다. POI 는 아직 쓰지 않는다 |

## 이미 있는 것 — 도장의 잔고 증명

「발행자가 검증한 특정 시점의 잔고」가 이미 온체인 스키마로 있습니다.

```
Balance Root      uint256 coinType, uint64 snapshotAt, uint192 leafCount,
                  uint256 totalAmount, bytes32 root          ← 머클 루트 1건
Verified Balance  uint256 balance, bytes32 salt, bytes32[] proofs   ← 포함 증명
```

발급자가 전체 잔고 트리의 **루트만** 온체인에 올리고, 사용자는 자기 몫에 대한
**포함 증명**을 제시합니다.

> **숨겨지는 것은 남의 잔고입니다. 본인 잔고는 아닙니다.**
> 위 스키마에서 `balance` 는 평문 필드라 증명을 제출한 사람의 잔고는 공개됩니다.
> GIWA 도 이 스키마를 「발행자로부터 검증받은 특정 시점의 잔고」라고 설명합니다.
> 「잔고를 밝히지 않고 보유만 증명」하려면 [ZK 술어](../limits/roadmap.md)가 필요합니다.

> 스키마 UID · 리졸버 주소는 [Dojang 컨트랙트 문서](https://docs.giwa.io/giwa-ecosystem/dojang/contracts)에 있고,
> 우리가 온체인에서 직접 읽어 확인했습니다.

## 구조가 같다 — 그래서 갈아엎지 않아도 된다

POI 의 술어와 머클 증명, 그리고 ZK 술어는 **같은 모양**입니다.

```
POI 결정         "BTC_PRICE_KRW_AT_END > 89,291,000 이다"
Verified Balance "내 잔고가 이 루트에 들어 있다"          — 남의 원장을 밝히지 않고 포함을 증명
ZK 술어          "내 잔고가 X 이상이다"                   — 값 자체를 밝히지 않고 조건을 증명
```

셋 다 **「전부 보여주지 않고 조건이 참임을 보인다」** 입니다.
다만 **숨기는 대상이 다릅니다** — 머클 증명은 남의 원장을, ZK 는 값 자체를 숨깁니다.

POI 는 이미 `salted commitment` 로 「무엇을 고정했는지 밝히지 않은 채 고정했음을 증명」합니다.
여기에 잔고 증명이 붙으면 **「그때 실제로 그 포지션을 들고 있었다」** 까지 붙습니다.
Verified Balance 의 UID 를 `evidenceCommitment` 의 원문에 넣으면 되므로
**결정 스키마를 바꿀 필요는 없습니다.**

> 단, 이때 확인하는 주체는 컨트랙트가 아닙니다. 컨트랙트는 `evidenceCommitment` 의
> 내용을 보지 않습니다. **공개(Reveal) 이후에 제3자가** 그 UID 를 온체인에서 조회해
> 확인하는 구조입니다.

## 지갑 안에서 성립하는 것

```
지갑이 이미 아는 것          POI 가 더하는 것
─────────────────           ─────────────────
누구인가 (Verified Address)  결과 전에 말했다는 시점
무엇을 들고 있나 (Balance)    그 말이 맞았는지의 산술 판정
                            틀렸을 때도 지워지지 않는다는 사실
```

지갑 밖 서비스는 앞의 두 줄을 **사용자에게 물어봐야** 합니다. 물어보는 순간
「본인이 원할 때만, 유리한 것만」이 되고, 그러면 기록의 의미가 사라집니다.
**POI 가 막으려는 것이 정확히 그것**입니다.

## 보자기(Bojagi) — 오면 무엇이 달라지나

| | |
|---|---|
| 현재 상태 | **개발자 문서 없음.** `docs.giwa.io/giwa-ecosystem/bojagi` 404, 생태계 목록에도 없음 (2026-07-30 확인) |
| 지금 대응 | salted commitment + 구간형 노출. 잔고는 도장 머클 증명으로 증명하되 값은 공개됩니다 |
| 오면 | 술어를 커밋으로 숨기고 정산 시 증명으로 대체하는 경로를 검토합니다 ([로드맵](../limits/roadmap.md)) |

**적용이 공짜는 아닙니다.** 지금 리졸버는 평문 `op · threshold` 로 `I17` 산술을
직접 계산하므로, 증명을 검증하는 **새 경로가 필요합니다.** 기존 필드에 증명 해시를
넣는 것만으로는 아무것도 검증되지 않습니다.

**의존하지도 않습니다.** 보자기가 나오지 않아도 POI 는 지금 그대로 동작합니다.

## 임베드 조건 — 확인된 사실

| | |
|---|---|
| 백엔드 | **없음.** 정적 파일 + RPC 직접 호출 |
| 라우팅 | 해시 라우팅 `#/d/<uid>` — 라우터 라이브러리 없음 |
| 지갑 인터페이스 | **EIP-1193 만** 요구. EIP-6963 다중 지갑 탐지 구현 |
| 지갑 없이 | 조회·검증 전부 동작 |
| 비용 | 결정 커밋 **1.21원**(실측), 서명 **1회** |

## 아직 확인하지 못한 것

* 월렛은 웹 콘텐츠를 어떤 방식으로 임베드하는가?
* 해시 라우팅·새로고침에 제약이 있는가?
* EIP-1193 서명 UX 는 외부 브라우저와 어떻게 다른가?
* 결정 상세로 연결하는 딥링크 규격은 무엇인가?
* 번들이 502KB 다 — 임베드 환경의 예산은 얼마인가?

**규격을 모르는 채 만들면 추측이 코드가 됩니다.** 그래서 월렛용 manifest·SDK adapter 를
지금 만들지 않았습니다. 이 질문들의 답을 GIWA 팀에게 듣는 것이 Phase 2 에서 가장 필요한 지원입니다.
