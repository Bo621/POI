## 1. 문제

### 1.1 거래는 남고 판단은 남지 않는다

```
남는 것     :  2026-05-14  BTC 매도  0.4개
남지 않는 것 :  왜 팔았는가
              무엇을 보고 그렇게 판단했는가
              그 판단이 언제 만들어졌는가
              선언한 조건이 실제로 일어났는가
```

### 1.2 사후 서사 재구성

```
결과 확인  →  그 결과를 설명하는 판단을 사후 작성  →  "내 판단대로 됐다"
```

거짓말 탐지로 잡히지 않는다. 진술 내용이 사실이기 때문이다. 다만 **그 진술이 만들어진 시점**이 기록되지 않았을 뿐이다.

### 1.3 통찰 — GitHub는 코드 저장소가 아니다

GitHub의 가치는 저장이 아니라 `git blame`이다. 커밋은 변경분이 아니라 **"왜 바꿨는가"**의 기록이다.

```
왜 손절 기준을 7% → 5%로 바꿨는가?
```

## 2. 증명 경계

> **이 장이 문서의 중심이다.** 본문·예시·스키마·KPI는 전부 이 장에 종속된다.

### 2.1 증명하는 것

| 명제 | 근거 | 강도 |
|---|---|---|
| **발행자가 t0에 어떤 내용을 확정했고 이후 바꿀 수 없다** | commitment | 강 |
| **공개(Reveal) 후: 공개된 내용이 t0에 확정된 것과 동일하다** | commitment 재계산 | 강 — **공개한 경우에만** |
| 커밋된 결정이 **이후 변조되지 않았다** | commitment + DAG 무결성 | 강 |
| 이 결정이 **발행 지갑(attester)에 귀속된다** | 서명 | 강 |
| 발행 지갑이 **커밋 시점에 Verified Address였다** | 커밋 시 UID 스냅샷 | 강 — **스냅샷을 남긴 경우에만** |
| **정산 결과가 관측값과 산술적으로 일치한다** | **컨트랙트 강제** | 강 |
| **관측 구간이 결정 시점 이후로만 설정됐다** | **컨트랙트 강제 (§2.5)** | 강 |
| 첨부된 **근거 commitment가 t0에 기록됐다** | commitment | 강 |
| 선언 조건의 **정산 결과가 재현 가능하다** | 출처·버전·로직 버전 기록 | 중 — §2.2 |
| 커밋된 결정이 **정산되지 않았다** | 정산 미발행 상태 노출 (§4.4) | 중 |
| **정산 결과에 이의가 제기됐다** | Challenge attestation (§4.3) | 중 |

> ⚠️ **commitment가 증명하는 것의 범위**
> commitment는 "발행자가 t0에 내용을 확정했고 바꿀 수 없다"를 증명한다. **그 내용이 무엇인지는 공개(Reveal) 전까지 제3자가 알 수 없다.**
> 따라서 "근거 자료가 존재했다"가 아니라 **"근거 commitment가 기록됐다"**가 정확한 서술이며, 내용 검증은 공개 이후에만 가능하다.

### 2.2 정산의 강도 — 독립 판정이 아니다

```
MVP      결정 소유자가 외부 데이터로 판정해 발행한다.
         출처·관측 시각·로직 버전을 함께 기록하므로
         제3자가 같은 절차로 결과를 재현할 수 있고,
         불일치 시 Challenge로 영구 기록할 수 있다.
         → 재현 가능성 + 이의 제기 가능성

Phase 2  오라클이 관측값을 독립 증명한다.
         → 독립 판정 (independent attestation)
```

**"독립"이라는 단어는 Phase 2 전용어로 예약한다.**

> **핵심**: 재현 가능성의 본질은 "누구나 **계산**할 수 있다"이지 "누구나 **제출**할 수 있다"가 아니다.
> 선언 조건이 평문으로 공개되므로 계산 가능성은 보장되고, 불일치는 Challenge로 드러난다.

### 2.3 증명하지 *않는* 것

| 명제 | 성격 |
|---|---|
| 이 이유가 진짜 이유였다 | **원리적 불가** — 내심의 상태는 관측 불가 |
| 이 근거가 결정을 유발했다 | **원리적 불가** — 자료의 존재 ≠ 인과 |
| 이 판단이 좋은 판단이다 | **설계상 배제** — 평가하지 않는다 |
| 정산에 쓰인 데이터 출처가 진실이다 | **현 단계 미지원** — Phase 2 오라클 |
| 모든 결정이 기록됐다 | **현 단계 미지원** — §2.4 |
| 모든 실행이 결정과 대응한다 | **현 단계 미지원** — §5 |
| 구간 내내 잔고가 유지됐다 | **현 단계 미지원** — §5.2 |

### 2.4 무결성 ≠ 완전성

| 속성 | 정의 | 현황 |
|---|---|---|
| **무결성** | 기록된 결정이 삭제·변조되지 않았다 | ✅ 증명 |
| **완전성** | 내린 결정이 전부 기록됐다 | ❌ **미증명** |

DAG는 기록된 노드의 변조를 막지만, **애초에 기록하지 않는 것**이나 **새 루트로 다시 시작하는 것**은 막지 못한다.

**Phase 2 설계 과제**: actor별 append-only 인덱스 / 활성 graph root 정의 / 분기·폐기 규칙 / 실행 데이터 대조

> 이 문서는 이 과제를 **해결됐다고 쓰지 않는다.**

### 2.5 사후 서사를 실제로 막는 것 — 컨트랙트 불변식

> **v0.9 신설.** 지금까지 "결과 이전에 고정한다"고 주장만 했고, **무엇이 그것을 강제하는지**는 쓰지 않았다.

```solidity
if (d.windowStart < block.timestamp) revert WindowInPast();   // I4
```

**관측 구간을 과거로 설정할 수 없다.** 이것이 사후 서사 차단의 실제 메커니즘이며, 컨트랙트가 트랜잭션을 실패시켜 강제한다.

그리고 이것만으로는 부족하다.

```solidity
if (graceSeconds < 1 hours || graceSeconds > 30 days) revert GraceOutOfRange(); // I6c
if (windowStart > block.timestamp + 30 days)  revert WindowStartTooFar(); // I6a
if (windowEnd - windowStart > 730 days)       revert WindowTooLong();     // I6b
```

**유예기간이나 관측 구간을 무한정 길게 잡으면 「정산 기한 경과」에 영원히 도달하지 않는다.** 상하한이 없으면 책임 회피가 합법적으로 가능해진다.

> 유예는 **초 단위**로 관리한다(최소 1시간, 최대 30일). 일 단위로 두면 최소 유예가 24시간이 되어 짧은 관측 구간을 쓰는 사용 사례와 데모가 모두 불편해진다.

**그리고 정산 결과 자체도 컨트랙트가 검증한다.**

```solidity
uint8 expect = _eval(op, observedValue, threshold) ? OBSERVED : NOT_OBSERVED;
if (result != expect) revert ResultMismatch();                            // I17
```

선언 조건이 평문으로 온체인에 있으므로, **관측값을 넣으면 결과 판정은 컨트랙트가 계산해 대조한다.** 발행자가 관측값과 모순되는 결과를 기록할 수 없다.

> 이로써 신뢰해야 하는 대상이 좁아진다. **산술 판정은 강제되고, 남는 것은 "관측값과 그 출처가 옳은가"뿐이다.** 이의(Challenge)는 정확히 이 지점을 겨냥한다.

### 2.6 네 가지 위조와 사정거리

| 유형 | POI |
|---|---|
| Fake Strategy — 변경 이유가 남지 않는다 | ✅ 시점 문제. 해결 |
| Fake Performance — 관측 구간을 사후에 정한다 | △ **부분** — 커밋한 결정에 한함 (§2.5로 강제). 애초에 커밋하지 않으면 재현됨 |
| Fake Identity — 불리한 결정을 기록하지 않거나 새로 시작한다 | △ **부분** — 완전성 문제 (§2.4) |
| Fake Reputation — 판단과 무관한 지표로 신뢰 구성 | △ 대안 제시일 뿐 |

## 3. Reason 설계

### 3.1 근본 문제

Reason은 **본질적으로 검증 불가능한 필드**다. 그리고 이유가 공개·영구 기록되는 순간, 합리적 사용자의 최적 전략은 **반증 불가능한 문장을 쓰는 것**이 된다.

```
"시장 상황 변화에 따른 리스크 조정"
"종합적 판단에 따른 비중 재조정"
```

전부 참이면서 전부 무의미하다.

### 3.2 객체 3계층

| 객체 | 저장 | DAG 노드 | predicate | 정산 | 증명하는 것 |
|---|---|---|---|---|---|
| `JOURNAL_ENTRY` | **오프체인 전용** | ✗ | — | — | **아무것도 증명하지 않음** |
| `TIMESTAMPED_NOTE` | 온체인 | ✗ (독립 노드) | — | — | 이 내용이 t0에 존재했고 변조되지 않았다 |
| `VERIFIABLE_DECISION` | 온체인 | ✓ (parent 링크) | **필수** | 가능 | 위 + 선언 조건의 정산 |

**역할**

- `JOURNAL_ENTRY` — 지갑 없이 쓰는 진입점. 검증 대상이 아님을 UI에 상시 표시
- `TIMESTAMPED_NOTE` — **이 계층만 놓고 보면 타임스탬프 서비스와 기능이 같다.** 차별점이 아니라 온램프
- `VERIFIABLE_DECISION` — 실제 제품

**승격 규칙**

| 경로 | t0 처리 |
|---|---|
| `JOURNAL_ENTRY` → 상위 | **승격 시점이 t0.** 소급되지 않음 |
| `TIMESTAMPED_NOTE` → `VERIFIABLE_DECISION` | **노트 내용의 t0는 보존.** predicate·정산은 승격 시점부터. **동일 지갑만 승격 가능**(컨트랙트 강제). 노트 내용이 결정 내용과 동일함은 보장되지 않는다 |

> "예전부터 말했다"를 증명하려면 **그 시점에 `TIMESTAMPED_NOTE`를 남겨야 한다.** 저널만 쓰다가 나중에 승격하는 것으로는 증명되지 않는다.

### 3.3 predicate — 시제 분리

| 필드 | 시제 | 의미 | 필수 |
|---|---|---|---|
| `trigger_predicate` | 과거·현재 | 결정 시점에 관측한 조건 | **필수** |
| `expected_outcome_predicate` | 미래 | 앞으로 일어날 것으로 선언한 조건 | 선택 |
| `settlement_window` | — | 언제, 어떤 데이터로 판정하는가 | **`expected_outcome_predicate`가 있을 때만** |
| `execution_rule` | 조건부 | 어떤 행동이 이 결정과 일치하는가 | Phase 2 |

**`expected_outcome_predicate`를 필수로 두지 않는 이유**

> "리스크를 줄이고 싶어서 비중을 낮춘다"

이건 예측이 아니라 선호다. 미래 predicate를 강제하면 사용자가 억지 예측을 지어내고, 이는 §3.1이 막으려던 뭉개짐이 다른 형태로 돌아오는 것이다.

### 3.4 검증 등급 — 원천으로만 구분

등급은 **서로 직교하는 두 축**으로 표시한다. 하나의 사다리로 합치면 표현할 수 없는 조합이 생긴다.

**축 1 — 근거 첨부**

| 등급 | 조건 | 추가로 검증되는 명제 | MVP |
|---|---|---|---|
| `SELF_DECLARED` | 조건 존재. 외부 판정 없음 | (형식 + 고정 시점만) | ✓ |
| `EVIDENCE_COMMITTED` | 근거 commitment 존재 | **근거 commitment가 t0에 기록됐다** | ✓ |
| `ORACLE_VERIFIED` | 관측값을 오라클이 독립 증명 | 관측값이 사실 | Phase 2 |

**축 2 — 공개 여부**

| 상태 | 조건 | 의미 |
|---|---|---|
| `SEALED` | 미공개 | 내용은 제3자가 알 수 없다 |
| `REVEALED` | 공개된 (salt, 원문)이 commitment와 일치 | **공개된 내용이 t0에 확정된 것과 동일하다** |

```
EVIDENCE_COMMITTED · SEALED     근거를 커밋했으나 내용은 비공개
EVIDENCE_COMMITTED · REVEALED   근거 내용까지 공개·검증됨
SELF_DECLARED · REVEALED        근거는 없으나 결정 본문은 공개·검증됨
```

> ⚠️ `ORACLE_VERIFIED`가 확인하는 것은 **"이것이 실제 이유였다"가 아니라 "predicate의 관측값이 사실이었다"**이다.
>
> ⚠️ **등급은 사용자가 입력하는 값이 아니라 첨부된 commitment로부터 파생되는 값이다.** 입력 필드로 두면 위조가 가능하다.

**등급은 품질이 아니라 형식에 대한 사실이다.** 외부 프로필에서 점수화·비교하지 않는다 (§8.3).

### 3.5 predicate가 하는 것과 하지 못하는 것

| | |
|---|---|
| **한다** | 결정에 **최소 하나의 반증 가능한 축**을 강제한다 |
| **하지 못한다** | 자유 텍스트 본문의 뭉개짐 자체를 제거하지 못한다 |

`free_text`는 계속 허용된다. **검증 대상이 아님을 UI에 명시**하고, 원문은 온체인에 올리지 않으며 salted commitment로만 앵커한다.

> **비대칭 주의**: `expected_outcome_predicate`는 평문이라 컨트랙트가 지표 화이트리스트를 강제하지만, `trigger_predicate`는 commitment 뒤에 있어 **온체인 강제가 적용되지 않는다.** 클라이언트가 같은 목록으로 안내하되 강제는 아니며, 이 차이를 UI와 문서에 명시한다.

## 4. Settlement (정산)

### 4.1 원칙 — 수익률이 아니다

```
✗ +12.4% / 목표 수익 달성
✓ 선언 조건이 정산 구간 내 관측됨 / 관측되지 않음 / 판정 불능
```

| 구분 | 값 |
|---|---|
| Settlement attestation `result` | `OBSERVED` / `NOT_OBSERVED` / `INDETERMINATE` |
| attestation 부재 시 파생 상태 | 「관측 시작 전」/「관측 중」/「정산 대기」/**「정산 기한 경과」** |
| 발행 시점에 따른 표시 | 「정산 완료」/ **「지각 정산」** (유예 경과 후 발행) |

### 4.2 정산 가능한 predicate만 허용한다

`expected_outcome_predicate`는 **MVP 관측 범위 안에서 판정 가능해야 한다.**

| | 예시 | MVP |
|---|---|---|
| ✅ 시장 관측 지표 | BTC 60일 최대낙폭, 30일 실현변동성, 가격대 도달 | 가능 |
| ✅ 온체인 관측 지표 | 컨트랙트 이벤트, 온체인 잔고 변화 | 가능 |
| ❌ 전략 성과 지표 | 전략 최대낙폭, 전략 수익률, Sharpe Ratio | **불가 — 실행 데이터 필요 (§5)** |
| ❌ 개인 자산 지표 | 개인 손익, 개인 포트폴리오 낙폭 | 불가 + 규제 검토 대상 |

**지표 화이트리스트를 컨트랙트에 등록하고, 등록되지 않은 지표는 트랜잭션이 거부된다.** 각 지표의 소수점 자릿수도 컨트랙트에 고정되어, **정산자가 달라도 같은 값으로 해석된다.**

### 4.3 Challenge — 거짓 정산을 드러내는 장치

> **v0.9 신설.**

정산은 **결정 소유자만** 발행할 수 있다. 그러나 **누구나 이의를 제기할 수 있다.**

| 계층 | 발행 권한 | 공식 결과 변경 |
|---|---|---|
| **Settlement** | 결정 소유자만 | ✓ |
| **Challenge** | **누구나** | ✗ — 나란히 기록 |

```
정산: 관측되지 않음      (발행자: 0x8f2c…a91b)
  ⚠ 이의가 제기된 정산입니다
     - 0x3f…  [검증 지갑]    관측됨  (관측값 18.4%, 출처: …)
     - 0xa2…  [미검증 지갑]  관측됨  (관측값 18.4%, 출처: …)
```

> **이의 "건수"는 표시하지 않는다.** 지갑 생성 비용이 사실상 0이라 건수는 언제든 부풀릴 수 있다.
> 목록으로만 보여주고 각 항목에 **검증 지갑 여부**를 병기한다. 정렬·랭킹에 쓰지 않는다 — §6.3 배지 정책과 동일한 원칙이다.
>
> 이의는 **철회 가능하다**(철회 후 재발행도 가능). 따라서 "영구 기록"이라고 서술하지 않는다.

**왜 정산 자체를 개방하지 않는가**

정산 권한을 누구에게나 열면 **그리핑 공격**이 성립한다. 공격자가 임의 결과로 선점 → 소유자는 발행 불가 → 공격자가 자기 것을 철회 → 상태가 「기한 경과」로 되돌아감 → 무한 반복. 비용은 가스비뿐이다.

소유권과 이의 제기를 분리하면 이 공격이 사라진다.

**그리고 이의가 겨냥하는 지점이 좁아졌다.** 정산 결과의 산술 판정은 컨트랙트가 강제하므로(§2.5), 발행자가 관측값과 모순되는 결과를 쓸 수 없다. 남는 분쟁 지점은 **"관측값과 데이터 출처가 옳은가"** 하나이며, 이의는 정확히 여기에 집중된다.

### 4.4 미발행 노출 — 그리고 그 한계

커밋된 결정은 t0에 이미 온체인에 있으므로, 정산하지 않는 것이 관측된다.

**공개 범위 통제의 예외**

> 선언 조건을 등록한 결정은 **정산 상태를 공개 범위 설정으로 숨길 수 없다.** 결정 내용과 이유는 비공개로 둘 수 있으나 정산 상태·이의 건수는 항상 공개된다. 이 규칙에 동의해야 선언이 가능하다.
>
> 정산을 발행했다가 **철회한 이력도 영구히 남는다.** 철회 후 「기한 경과」로 되돌아가더라도, 처음부터 정산하지 않은 것과 구별된다.

**한계**

- 이 규칙은 **커밋된 결정에만 적용된다.** 애초에 커밋하지 않은 결정은 여전히 탐지되지 않는다 (§2.4)
- 따라서 "숨길 수 없다"가 아니라 **"커밋한 이상 숨길 수 없다"**가 정확한 서술이다

### 4.5 미해결 긴장

예측 관측 여부를 장기 누적하면 **캘리브레이션 기록**이 되고, "이 사람은 예측을 잘한다"로 읽힌다. 즉 평가에 가까워진다.

1. 적중 관련 수치를 외부 프로필에 노출하지 않는다 (§8.3)
2. 사용자 간 비교·랭킹·리더보드 미제공
3. API 응답에서 정렬 키로 노출 금지
4. **미관측 결과도 동일한 시각적 비중으로 표시**
5. Phase 2 진입 전 법률 검토

### 4.6 Commit-Reveal

> **v0.9 신설.** 재현 가능성이 실제로 작동하는 절차다.

```
t0   커밋
     결정 내용·이유·근거는 salted commitment로만 온체인에 남긴다
     선언 조건과 정산 구간은 평문으로 공개된다

t1   정산
     소유자가 발행. 제3자도 같은 데이터로 계산 가능 (선언 조건이 평문이므로)

t1+  이의 (선택)   불일치 시 누구나 발행

t1+  공개 (선택)   (salt, 원문)을 공개하면 누구나 commitment를 재계산해
                  t0 내용이 조작되지 않았음을 확인할 수 있다
```

| 성질 | |
|---|---|
| t0 이후 내용 변경 | ❌ 불가 |
| 원문을 몰라도 정산 계산 | ✅ 가능 |
| **공개가 정산의 전제인가** | **❌ 아니다** |
| 공개 거부 | ✅ 가능 — 단 결정 내용은 "미공개"로 표시 |
| **salt 분실** | **공개 영구 불가.** UI가 백업을 강제 유도 |

## 5. Execution — 관측 한계

### 5.1 Verified Balance 정정

도장 **Verified Balance는 특정 시점의 잔고 스냅샷**이며 체결·주문 이벤트가 아니다. 따라서 **몇 번 매매했는가 / 각 실행이 언제 일어났는가 / 각 실행이 어느 결정에 대응하는가**를 알 수 없다.

실행 정합성 배지는 **MVP에서 제공하지 않는다.**

### 5.2 남는 것도 과장하지 않는다

```
✗ "검증된 잔고를 6개월간 유지했다"
   → 스냅샷 사이에 0이 되었다 복구돼도 탐지되지 않는다

✓ "6개월에 걸쳐 3회 이상의 시점에서 잔고가 검증됐다"
```

**스냅샷 발급 주기가 미확인**이므로 관측 해상도를 특정할 수 없다. 배지 문구는 **횟수와 기간을 함께 표기**하고 "유지"라는 단어를 쓰지 않는다.

### 5.3 Phase 2 선택지

| 경로 | 비용 |
|---|---|
| A. 온체인 거래만 Execution으로 인정 | 즉시 구현. **업비트 사용자 기반과의 연결이 약해짐** |
| B. 거래소 execution attestation 신설 | 두나무 협의 필요 |
| C. 업비트 Open API | 약관 확인 필요. 전환율 저하 |

**MVP는 셋 다 채택하지 않는다.** 도입 시 배지명은 `Observable Execution Coverage`로 하고 데이터 원천과 관측 범위를 병기한다.

### 5.4 Open API 필요 여부

| 기능 | Open API | 단계 |
|---|---|---|
| 결정 커밋·불변성 증명 | 불필요 | MVP |
| Reason 형식·등급 판정 | 불필요 | MVP |
| 정산 (시장·온체인 지표) | 불필요 (공개 데이터) | MVP |
| 스냅샷 시점 잔고 배지 | 불필요 (Verified Balance) | Phase 2 |
| **실행 정합성 검증** | **경로 B 또는 C 필요** | Phase 2 |

MVP 범위에서 **사용자 자격증명 의존은 없다.** 단 GIWA Chain·EAS·도장에는 의존한다.

### 6.1 Strategy Passport 예시

```
Momentum BTC v2.1                          작성자: 0x8f2c…a91b

─── 온체인 결정 그래프 ────────────────────────────────

D1  전략 생성                       등급: EVIDENCE_COMMITTED
    관측 조건    BTC 30일 실현변동성 > 60.0%
                 관측값 62.4%  (출처·시각 기록)
    근거         commitment 0x…  (백테스트 결과)
    선언 조건    없음  →  정산 없음

D2  손절 기준 7% → 5%    parent: D1   등급: EVIDENCE_COMMITTED
    관측 조건    BTC 30일 실현변동성 > 60.0%   관측값 62.4%

    정산 결과    관측되지 않음  (관측값 23.1%)
                 2026-06-30 발행 · 출처·버전 기록
                 ⚠ 이의 1건

    관측 조건    ETH/BTC 비율 > 0.055   관측값 0.058
    선언 조건    없음  →  정산 없음

```

> D2가 **"관측되지 않음"인 것은 의도된 예시다.** 미관측 결과를 동일한 비중으로 보여주는 것이 §4.5-4의 원칙이다.

### 6.2 Trader Passport (Phase 2)

> MVP 산출물이 아니다.

```
0x8f2c…a91b

✓ Verified Address                            (도장)
✓ 온체인 활동 3년 이상 — 이더리움 기준         (온체인)
✓ 6개월에 걸쳐 3회 이상 시점 잔고 검증          (Verified Balance)
✓ 검증 가능 결정 10건 이상                     (POI)
✓ 정산 완료 10건 이상                          (POI)
```

**공개하지 않는 것**: 실명, 전체 자산, 정확한 잔고, 손익, 개별 주문, API 키, 출금 주소, 거래소 회원번호

### 6.3 배지 정책

단일 Trust Score를 제공하지 않는다. 배지 개수도 사실상 점수로 작동하므로 다음을 금지한다.

- 배지 개수·희소성 기준 정렬 (등록 시점순 고정)
- 사용자 간 배지 비교 UI
- 랭킹, 리더보드, "상위 n%" 표현
- API 응답에서 배지 개수를 정렬 키로 노출
- **외부 프로필에서** 검증 등급·정산률의 수치화·비교

**설계 원칙**: 사실 기반 / 조건 공개 / 발급 시점 공개 / 검증 방법 공개 / 만료일 표시 / 철회 가능 / 양도 불가 / 금전적 권리 없음

## 7. 콜드스타트

### 7.1 역설

검증의 효용이 큰 사람은 이미 팔로워가 있는 층인데, 이들은 과거 이력 노출을 가장 피하고 싶어 한다. 검증에 응할 사람은 아직 팔로워가 없어 효용이 없다.

### 7.2 계층별 진입 비용 분할

| 단계 | 객체 | 얻는 것 | 필요한 것 |
|---|---|---|---|
| 1 | `JOURNAL_ENTRY` | **"왜 샀는지" 기록.** 혼자 써도 완결 | 없음 |
| 2 | `TIMESTAMPED_NOTE` | **"내가 이 시점에 말했다"** 증명 | 지갑 + **약 0.3원** (§12.1 실측) |
| 3 | `VERIFIABLE_DECISION` | 선언 조건의 정산 이력 | + 조건 작성 |
| 4 | 외부 재사용 | 커뮤니티·플랫폼의 attestation 조회 | 팔로워 |

**핵심**: 2단계 비용이 원 단위 미만이므로 **"나중에 증명해야 할지도 모르는" 상태에서도 부담 없이 남길 수 있다.** 저비용 체인이 제품을 가능하게 하는 지점이다.

### 7.3 초기 타깃

| 세그먼트 | 진입 동기 |
|---|---|
| 기록 습관이 있는 개인 투자자 | 판단 저널. 타인 불필요 |
| 콘텐츠 크리에이터 (신규) | 지금 한 말을 나중에 증명 (2단계) |
| 퀀트·자동매매 개인 개발자 | 이미 Git을 쓰는 층 |
| **투자 커뮤니티 운영자** | **운영자 도입 → 구성원 다수 유입. 성장 축** |

## 8. KPI

### 8.1 미스매치 인정

| KPI | 현황 |
|---|---|
| TVL | **0** — 자산 수탁을 하지 않는다. TVL은 DeFi/RWA 트랙 지표 |
| 트랜잭션 수 | §8.2 산식 |
| 사용자 수 | 계층 진입으로 대응 (§7.2) |

### 8.2 트랜잭션 산식

**활성 사용자 1인당 연간 온체인 트랜잭션**

```
= 12n                    노트 발행
+ 12c                    결정 커밋
+ 12·c·r·s               정산 발행
+ 2·12·c·r·s·f           정산 정정 (철회 + 재발행)

n : 월 노트 수      c : 월 결정 수      r : 선언 비율
s : 정산 발행률     f : 정정률
```

| 시나리오 | n | c | r | s | f | 연간 TX |
|---|---|---|---|---|---|---|
| 보수 | 0 | 1 | 0.30 | 0.70 | 0.05 | **15** |
| 기준 | 1 | 3 | 0.50 | 0.70 | 0.05 | **62** |
| 적극 | 2 | 8 | 0.60 | 0.80 | 0.10 | **175** |

> 배지 재검증은 MVP 사양이 없으므로 산식에서 제외했다. 제3자 이의는 사용자 1인당 산식에 넣지 않는다(네트워크 총량에는 더해진다).

## 10. GIWA 기술 스택

> 이 장의 모든 값은 **2026-07-27 GIWA Sepolia RPC 실측**이다 (§0.1).

### 10.1 EAS와 POI 컨트랙트의 역할

| 담당 | 주체 |
|---|---|
| attestation 레지스트리, 발급·조회·철회 | **EAS** — 재구현하지 않음 |
| 스키마별 불변식 강제 | **POI Resolver** — EAS가 발행 직전 호출하는 훅 |
| 정산 판정 로직 | **오프체인 verifier** — 버전 기록 |

> **"POI 앵커 컨트랙트"의 정체는 EAS SchemaResolver다.**
> 레지스트리를 새로 만드는 것이 아니라, EAS가 attestation 발행 직전에 호출하는 훅에 검증 로직을 넣는다. 불변식을 위반하면 **트랜잭션이 실패한다.**
> 이 구조에서 "자체 레지스트리를 만들지 않는다"와 "컨트랙트를 배포한다"가 동시에 참이 된다.

**이식성**

EAS 표준을 쓰므로 POI attestation은 **EAS 지원 도구에서 조회 가능하다.** 이는 이식을 어렵게 만들지 않는다. POI가 GIWA에 결속되는 이유는 **락인이 아니라 데이터 원천(도장·Upbit Oracle)과 수수료 구조**다.

### 10.2 도장(Dojang) — 동작 확인 완료

```
DojangScroll  0xd5077b67dcb56caC8b270C7788FC3E6ee03F17B9   v0.5.1
isVerified(address, bytes32) → bool                        정상 동작 확인
Attester ID   keccak256("dojang.dojangattesterids.upbitkorea")
            = 0xd99b42e7…53034                             문서값과 일치 확인
```

| Attestation | POI 활용 | 단계 |
|---|---|---|
| Verified Address | 지갑 검증. 검증 지갑 교체 비용 상승 | MVP |
| Verified Balance | 스냅샷 시점 잔고 검증 (§5.2) | Phase 2 |
| Balance Root | Verified Balance 검증 참조 | — |
| Verified Code | 계정 연결 플로우 | — |

### 10.3 up.id — 서술 정정

> **v0.9 정정.** v0.8은 up.id를 GIWA 선택 근거 중 하나로 들었으나, **GIWA Sepolia에 ENS 레지스트리가 배포되어 있지 않다** (실측 확인).

| 사실 | 함의 |
|---|---|
| up.id는 ENS 서브도메인 (`username.up.id`) | 이름 해석은 **ENS가 배포된 체인**에서 일어난다 |
| GIWA Sepolia에 ENS 미배포 | **GIWA 컨트랙트가 up.id를 직접 조회할 수 없다** |
| 해석 경로 | 클라이언트가 별도 체인 RPC로 조회하거나, 크로스체인 해석(CCIP-Read) 필요 |

**MVP 대응**

- up.id 표시는 **UI 편의 기능**으로 격하한다. 온체인 로직은 지갑 주소로만 동작한다
- ENS 조회가 불가능하면 **주소 축약 표기**(`0x8f2c…a91b`)로 대체한다
- 신원 결속의 근거는 **up.id가 아니라 도장 Verified Address**다

> 이 정정으로 §12.1 "왜 GIWA인가"에서 up.id 항목은 근거에서 빠지고, **Verified Address가 그 역할을 대신한다.**
> 남은 확인 사항: up.id가 어느 체인에 등록되어 있는지, 크로스체인 해석 지원 계획이 있는지 (부록 B.5)

### 10.4 Upbit Oracle / 보자기 — 의존하지 않음

- **Upbit Oracle** — `ORACLE_VERIFIED`의 전제. 개발자 문서가 스텁 상태로 제공 데이터 미공개. MVP는 공개 데이터로 정산 (§2.2)
- **보자기(Bojagi)** — ZK 프라이버시 프로토콜로 발표됐으나 **개발자 문서에 페이지 없음.** MVP는 구간형 노출 정책 + salted commitment로 대응. predicate 형태가 **ZK 술어와 구조적으로 유사**하므로 공개 시 적용을 검토한다


### 12.2 고비용 체인에서 무너지는 지점

저비용은 "있으면 좋은 것"이 아니다. **비용이 커밋 빈도를 정하고, 커밋 빈도가 t0의 해상도를 정한다.**

같은 120,000 gas를 이더리움 L1에서 쓰면 이렇게 된다.

```
                  가스 가격      커밋 1건      결정 커밋 36건/년
GIWA        0.001 gwei          1.21원              19원
이더리움 L1     10 gwei        850원         181,000원

동일 가정: 120,000 gas · ETH $3,000 / 1,400원.
L1 가스 가격 10 gwei는 예시값이며 실제로는 크게 변동한다.
36건은 §8.2 기준 시나리오의 결정 커밋(c=3/월)만이며, 노트·정산 비용은 제외했다.
GIWA의 1.21원에는 L1 데이터 0.03원이 포함돼 있다. 실행 가스만 비교하면 정확히 10,000배다.
```

약 **702배**다. 이 비용을 그대로 지불하거나 서비스가 보조할 수도 있다. 그러나 **비용을 줄이는 쪽을 택하면** 대표적인 두 갈래가 있고, 둘 다 POI를 깎아낸다.

**갈래 1 — 여러 결정을 한 트랜잭션에 묶는다.**

결정마다 별도 EAS UID를 갖는 구조(부록 B.2)는 유지된다. 그래서 아끼는 것은 **트랜잭션 기본 가스 21,000뿐**이고, 결정마다 드는 저장·resolver 가스 약 99,000은 그대로 남는다. 30건을 한 번에 묶어도 건당 850원 → 약 4,160원, **17% 절감**이다.

게다가 **Decision Graph의 부모-자식 연결이 끊긴다.** EAS는 한 배치의 모든 attestation에 같은 블록 timestamp를 넣는데, 불변식 I2는 부모가 자식보다 **엄격히** 빨라야 한다고 강제한다.

```solidity
if (p.time >= a.time) revert ParentNotEarlier();   // I2
```

따라서 한 달간 순차적으로 내린 결정들을 한 배치 안에서 `D1 → D2 → … → D30`으로 연결하면 트랜잭션 전체가 실패한다. 묶으려면 모두 배치 이전 head를 부모로 삼는 형제 노드로 만들거나 부모 링크를 생략해야 하고, 그러면 **한 달치 판단의 선후 관계가 사라진다.** 전략이 어떤 순서로 바뀌었는지가 Decision Graph의 내용인데, 그것이 남지 않는다.

절감은 17%뿐이고 잃는 것은 그래프 구조다. **배치는 고비용 문제를 풀지 못한다.**

**갈래 2 — 한 달치를 집계 commitment 하나로 묶는다.**

비용은 실제로 줄어든다. 대신 **개별 결정에 온체인 식별자가 없어진다.** 정산과 미발행 상태는 decision UID를 참조하고, Challenge는 그 결정에 달린 settlement UID를 참조하므로, 셋 다 붙을 대상이 사라진다. 남는 것은 "이 시각에 무언가를 생각했다"는 해시 하나다.

그리고 어느 갈래를 택하든 커밋은 모아서 하게 되므로 t0가 늦어진다. 온체인이 보증하는 것은 *커밋한 시각*이므로 **그 이전에 일어난 사건에 대해서는 선행성을 증명할 수 없다.** (이후 사건이라면 한 달 이내여도 증명된다 — 잃는 것은 증명 자체가 아니라 증명이 닿는 범위다.) §2.5의 불변식이 `windowStart >= 커밋 시각`을 강제하므로 관측 구간도 그만큼 늦게 열린다. 지연은 결정 시점에 따라 0에서 배치 주기 사이다.

| | GIWA<br>결정 단위 커밋 | 고비용 · 갈래 1<br>트랜잭션 묶기 | 고비용 · 갈래 2<br>집계 commitment |
|---|---|---|---|
| 결정 건당 비용 | 1.21원 | 약 4,160원 (17% 절감) | 낮음 |
| 개별 결정 UID | 있음 | 있음 | **없음** |
| 정산 · 미발행 · Challenge | 작동 | 작동 | **참조 대상 없음** |
| 결정 간 선후 관계 (I2) | 보존 | **끊김** | 없음 |
| t0 해상도 | 분 | 배치 주기 | 배치 주기 |

> **결론.** 고비용 체인에서 POI의 스키마와 불변식 자체가 깨지지는 않는다. 비용을 그대로 지불하면 기능도 그대로다. 나빠지는 것은 **비용을 줄이려 할 때 치러야 하는 대가**다 — 갈래 1은 결정 간 선후 관계를, 갈래 2는 정산·미발행·Challenge가 참조할 대상을 잃는다. GIWA의 비용 구조는 결정 단위 커밋을 현실적인 기본값으로 만들어 이 선택 자체를 하지 않아도 되게 한다.

> **"다른 체인에서는 불가능하다"고 쓰지 않는다.**
> "GIWA에서 차별화가 강화되고, 고비용 체인에서는 경제성과 시점 해상도가 나빠진다"가 방어 가능한 서술이다.

## 15. 예상 질문

**"결국 투자자문 아닙니까?"**
종목·시점·비중·전략을 추천하지 않습니다. 결정이 언제 기록됐고 선언 조건이 관측됐는지만 판정합니다.

**"이유가 거짓이면요?"**
POI는 이유의 진실성을 검증하지 않습니다. **이유가 결과 이전에 고정됐고 수정되지 않았음**을 검증합니다. 검증 대상 결정은 반증 가능한 조건을 필수로 요구하지만, **자유 텍스트의 모호함을 완전히 제거하지는 못합니다.**

**"결과를 보고 나서 유리하게 구간을 잡으면 되지 않나요?"**
**컨트랙트가 막습니다.** 관측 구간의 시작이 커밋 시점보다 과거이면 트랜잭션이 실패합니다. 유예기간과 구간 길이에도 상하한이 있어 「기한 경과」를 무한정 미룰 수 없습니다. (§2.5)

**"좋은 결정만 골라 기록하면 되지 않나요?"**
**부분적으로만 막습니다.** 커밋한 결정의 정산 미발행은 공개 범위 설정으로도 숨길 수 없고, 정산을 철회한 이력도 남습니다. 그러나 **애초에 커밋하지 않은 결정은 탐지하지 못합니다** (§2.4).

**"정산을 본인이 하면 POI나 발행자를 믿어야 하는 것 아닙니까?"**
선언 조건이 평문으로 공개되므로 **누구나 같은 데이터로 계산할 수 있습니다.** 결과가 다르면 이의(Challenge)를 온체인에 영구 기록할 수 있고, 이의 건수는 정산 옆에 항상 표시됩니다. 다만 MVP 정산은 독립 판정이 아니라 **재현 가능성**을 제공합니다. 독립 판정은 오라클 연계 이후입니다.

**"왜 정산을 아무나 못 하게 했습니까?"**
개방하면 그리핑 공격이 성립합니다. 공격자가 임의 결과로 선점한 뒤 철회하면 상태가 「기한 경과」로 되돌아가고, 이를 무한 반복할 수 있습니다. 소유권과 이의 제기를 분리해 이 공격을 제거하면서 거짓 정산이 드러나는 성질은 유지했습니다. (§4.3)

**"업비트 Open API를 못 쓰면요?"**
MVP 전 범위가 영향받지 않습니다. 실행 정합성 검증(Phase 2)에만 추가 데이터 원천이 필요합니다.

**"도장이 거래내역을 검증해 줍니까?"**
아닙니다. 도장은 Verified Address와 **잔고 스냅샷**을 발급합니다. 체결 이벤트는 제공하지 않습니다.

**"타임스탬프 서비스와 뭐가 다릅니까?"**
노트 계층만 놓고 보면 같습니다. 그건 온램프입니다. 차별점은 **도메인 스키마 + 관측 구간 소급 차단 + 정산 규율 + 미발행·이의 노출**입니다.

**"왜 GIWA입니까?"**
§12.1. EAS가 프리디플로이되어 있고(v1.4.1 확인), 도장이 KYC 결속 신원을 제공하며(v0.5.1 확인), 트랜잭션 비용이 원 단위 미만(실측 1.21원)이라 결정 단위 커밋이 성립합니다.

**"배지가 투자 실력을 의미합니까?"**
아닙니다. 특정 사실이 확인됐다는 의미일 뿐입니다.

# 부록 A. 규제 상세

## A.1 자본시장법

투자판단에 관한 추천·자문을 제공하면 투자자문업 이슈가 발생할 수 있다. **초기 범위를 가상자산 투자 의사결정 검증으로 한정한다.**

**허용 표현**
- 이 결정은 2026년 5월 2일에 기록됐습니다
- 기록 이후 수정되지 않았습니다
- 관측 구간은 기록 시점 이후로만 설정할 수 있습니다
- 선언한 조건이 정산 구간 내 관측됐습니다 / 관측되지 않았습니다
- 6개월에 걸쳐 3회 이상 시점에서 잔고가 검증됐습니다

**금지 표현**
- 우수한 판단입니다 / 정확한 예측입니다
- 수익 가능성이 높습니다 / 초보자에게 적합합니다 / 안전한 전략입니다
- **검증된 잔고를 6개월간 유지했습니다** ← 관측 불가 (§5.2)

## A.2 금융소비자보호

판매·중개·자문을 하지 않는 검증 인프라에 머무르면 금융상품판매업자와 거리가 있다.
**추가 시 별도 검토**: 금융상품 추천 / 맞춤 추천 / 성향 분석 후 상품 연결 / 제휴 광고 / 수익률 중심 홍보 / 전략 판매·중개 / 판단 품질 평가

## A.3 가상자산 규제

**하지 않는 행위**: 매매 / 교환 / 이전 / 자산 보관 / 매매 중개 / 출금 대행 / 공동 운용 / 자동 주문

**배지 정책**: 양도 불가 / 거래 불가 / 상장 불가 / 금전적 권리 없음 / 수익 배분 없음 / 담보 기능 없음 / 만료·철회 가능

## A.4 개인정보보호

- Reason 원문 온체인 기록 금지
- **단순 해시는 대응책이 아니다.** 짧고 예측 가능한 문장은 사전 대입으로 복원된다
- **salted commitment 필수** — 128비트 salt, 클라이언트 생성, 온체인 기록 금지
- **도메인 분리자 적용** — 결정·조건·근거·이유 commitment가 서로 교차 검증되지 않도록
- 원문 공개는 사용자 선택. 입력 단계에서 개인정보 포함 경고

## A.5 업비트 Open API (Phase 2 조건부)

**권한**: 조회 전용만. 주문·입금·출금 권한 요청 금지
**키 관리**: 암호화 저장, 최소 권한, 검증 후 즉시 폐기 우선, 접근 로그, 연결 해제 기능
**데이터**: 원본 재판매 금지, 개별 체결 공개 금지, 제3자 원본 제공 금지, 검증 결과만 공개
