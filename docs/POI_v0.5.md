# Proof of Investing

**Decision Graph — GIWA 기반 투자 의사결정 검증 인프라 기획서 v0.5**

> **v0.4 → v0.5 주요 변경**
> 1. **서사 전환: Trading → Decision** — 증명 대상을 "투자 활동"에서 **"투자 의사결정"**으로 재정의했다. Pre-Commit 프로토콜은 폐기되지 않고 Decision 노드로 일반화된다.
> 2. **Decision Graph 도입** — Decision → Reason → Evidence → Execution → Outcome. Git의 DAG 구조를 그대로 채택한다.
> 3. **Reason 스키마 신설 (핵심)** — 이유를 자유 텍스트가 아니라 **반증 가능한 predicate**로 받는다. POI는 이유의 진실성을 검증하지 않고, **이유의 형식과 고정 시점**만 검증한다.
> 4. **검증 등급 체계** — Unverified / Evidence-linked / Oracle-anchored. 내용 평가가 아닌 형식에 대한 사실.
> 5. **Outcome 정의 확정** — 수익률이 아니라 **"선언한 조건이 관측됐는가"**. 미해결 규제 긴장을 명시.
> 6. **Unexplained Execution 배지 신설** — 실행 데이터와 결정 그래프를 대조해 선택 편향을 탐지한다.
> 7. **콜드스타트 재작성** — 진입점을 "전략 버전 관리"에서 **"투자 의사결정 저널"**로 변경. 네트워크 효과 0에서도 성립.
> 8. **MVP 구현 범위는 v0.4와 동일** — 서사와 스키마만 상위 개념으로 이동. 4일 내 산출물이 늘지 않는다.

## 0. 요약

| 항목 | 내용 |

| 프로젝트명 | Proof of Investing (POI) |
| 핵심 프리미티브 | **Decision Graph** |
| 한 줄 정의 | 투자 의사결정을 결과가 나오기 전에 고정하고, 그 결정과 실제 행동의 정합성을 검증하는 GIWA 네이티브 인프라 |
| 증명 대상 | 수익률 ✗ / 거래 이력 △ / **의사결정 ✓** |

| 외부 의존 | **없음** (업비트 Open API 불필요) |

### 한 문장 피치

> 투자에서 남는 건 거래 기록이 아니라 **판단**입니다.
> 그런데 판단만 아무도 기록하지 않습니다.
> **POI는 결정을, 결과를 알기 전에 고정합니다.**

## 1. 문제 재정의

### 1.1 정보 부족이 아니라 검증 불가능성

투자 정보는 이미 넘친다. 검증할 수 없을 뿐이다.

- 이 사람이 실제 투자 경험이 있는가
- 이 전략이 실제로 운영된 적이 있는가
- 백테스트가 사후에 유리하게 조정되지 않았는가
- 불리한 기록을 삭제하지 않았는가
- 계정을 새로 파서 이력을 초기화하지 않았는가

### 1.2 그러나 진짜 문제는 더 깊은 곳에 있다

위 항목은 전부 **"무엇을 했는가"**에 대한 질문이다. 그런데 투자에서 실제로 반복 가능하고, 배울 수 있고, 신뢰의 근거가 되는 것은 행동이 아니라 **판단**이다.

거래 기록은 남는다. 증권사도, 거래소도, 세무 자료도 남긴다.
**판단은 아무 데도 남지 않는다.**

```
남는 것    :  2026-05-14  BTC 매도  0.4개
남지 않는 것:  왜 팔았는가
             무엇을 보고 그렇게 판단했는가
             그 판단이 언제 만들어졌는가
             그 판단이 맞았는가
```

### 1.3 그래서 벌어지는 일 — 사후 서사 재구성

현재 구조에서 가장 흔한 기만은 거짓말이 아니라 **사후 서사 재구성**이다.

```
결과 확인  →  그 결과를 설명하는 판단을 사후 작성  →  "내 판단대로 됐다"
```

이건 거짓말 탐지로 잡히지 않는다. 진술 내용이 사실이기 때문이다. 다만 **그 진술이 만들어진 시점**이 기록되지 않았을 뿐이다.

**POI가 푸는 문제는 정확히 이 시점 문제다.**

### 1.4 네 가지 위조 — Decision 관점 재해석

| 유형 | v0.4 정의 | Decision 관점 |
|---|---|---|
| Fake Performance | 백테스트 구간·조건 선택 | **관측 구간을 사후에 정한다** |
| Fake Identity | 새 계정으로 이력 소거 | **불리한 결정 노드를 통째로 지운다** |
| Fake Reputation | 팔로워·평점 조작 | 판단의 질과 무관한 지표로 신뢰를 구성 |
| Fake Strategy | 이전 버전 소멸 | **변경 이유가 남지 않는다** |

네 가지 모두 **"결정이 결과보다 먼저 고정되지 않았다"**는 하나의 원인으로 환원된다.

## 2. Decision Graph

### 2.1 통찰: GitHub는 코드 저장소가 아니다

GitHub의 가치는 저장이 아니라 `git blame`이다. **"이 줄이 왜 여기 있는가"**에 답할 수 있다는 것.

커밋은 변경분이 아니라 **"왜 바꿨는가"**의 기록이다. 개발자 생태계의 신뢰는 코드가 아니라 이 이유의 누적에서 나온다.

투자도 같다.

```
왜 손절 기준을 7% → 5%로 바꿨는가?
```

이걸 저장하는 순간 프로젝트의 성격이 바뀐다.

```
[기존]  투자 이력  →  증명

[POI]   투자 의사결정  →  증명  →  변경 이유  →  실행  →  결과
```

### 2.2 다섯 노드

```
Decision  ──→  Reason  ──→  Evidence
    │
    ├──────→  Execution
    │
    └──────→  Outcome
```

| 노드 | 내용 | 검증 가능성 |
|---|---|---|
| **Decision** | 무엇을 결정했는가 | ✅ 사실 — 발생과 시점 |
| **Reason** | 왜 그렇게 결정했는가 | ⚠️ **내심의 상태. 직접 검증 불가** |
| **Evidence** | 무엇을 근거로 삼았는가 | △ 자료 존재는 사실. 인과는 아님 |
| **Execution** | 실제로 그렇게 행동했는가 | ✅ 사실 |
| **Outcome** | 선언한 조건이 관측됐는가 | ✅ 사실 |

### 2.3 그래프 구조는 Git에서 그대로 가져온다

커밋이 부모 커밋을 참조하듯, 결정은 이전 결정을 참조한다.

```
D1 (전략 생성)
 └─ D2 (손절 7% → 5%)          parent: D1
     ├─ D3 (BTC 매수)           parent: D2
     └─ D4 (ETH 조건 추가)      parent: D2
         └─ D5 (포지션 비중 조정) parent: D4
```

Merkle DAG이므로 다음이 자동으로 따라온다.

- 임의의 결정에서 루트까지 경로 추적 가능
- 중간 노드 변조 시 하위 전체 해시 불일치
- 부분 공개 가능 (특정 서브트리만 노출)
- 자료구조를 새로 설계할 필요 없음

## 3. Reason 문제 — 그리고 해법

> **이 장이 v0.5의 핵심이다.** 여기가 무너지면 전체가 무너진다.

### 3.1 문제 인식

POI의 브랜드 전체는 **"사실만 검증한다, 주장은 검증하지 않는다"**이다.
그런데 Reason은 **본질적으로 검증 불가능한 필드**다. 내심의 상태에 대한 주장이기 때문이다.

검증 불가능한 필드를 검증 제품의 한복판에 놓으면 자기 전제를 깬다.

실무적 붕괴도 명확하다. 이유가 공개되고 영구 기록되는 순간, 합리적 사용자의 최적 전략은 **반증 불가능한 문장을 쓰는 것**이 된다.

```
"시장 상황 변화에 따른 리스크 조정"
"종합적 판단에 따른 비중 재조정"
```

전부 참이면서 전부 무의미하다. 이유 필드에 걸린 굿하트의 법칙이다.

### 3.2 해법 1 — 진실성이 아니라 고정 시점을 검증한다

**POI는 "이 이유가 진실이다"를 보증하지 않는다.**
**POI는 "이 이유가 t0에 기록됐고 이후 수정되지 않았다"를 보증한다.**

이건 사실이고, 체크 가능하고, POI 원칙을 깨지 않는다.

Git도 커밋 메시지의 정직성을 검증하지 않는다. 불변성과 귀속성만 보장한다. 그것만으로 개발자 생태계의 신뢰 인프라가 됐다.

> **핵심 문장**
> 우리는 이유를 검증하지 않습니다.
> **이유를 반증 가능한 형태로만 받습니다.**

### 3.3 해법 2 — 스키마가 뭉개짐을 거부하게 만든다

자유 텍스트를 받지 않는다. Reason은 **최소 1개의 반증 가능한 predicate**를 포함해야 한다.

```
✗ 거부
{
  "reason": "변동성이 올라서"
}

✓ 수용
{
  "predicate": {
    "metric": "BTC_30D_REALIZED_VOL",
    "operator": ">",
    "threshold": 60,
    "source": "upbit_oracle"
  },
  "observation_window": "30d",
  "free_text": "변동성 확대 국면에서 손절 폭을 좁힘"   // 보조 설명
}
```

핵심은 **희망이 아니라 설계 제약**이라는 점이다. 형식이 뭉개진 문장을 물리적으로 거부한다.

`free_text`는 허용하되 **검증 대상이 아님을 UI에 명시**한다.

### 3.4 해법 3 — 품질이 아니라 검증 가능성으로 등급화한다

| 등급 | 조건 | 의미 |
|---|---|---|
| **Unverified** | 자유 텍스트만 | 기록됐고 수정되지 않았음 |
| **Evidence-linked** | 증거 해시 첨부 | 근거 자료가 결정 시점에 존재했음 |
| **Oracle-anchored** | predicate가 온체인 데이터로 판정 가능 | 이유의 사실 관계를 독립 검증 가능 |

**이것은 이유의 내용에 대한 판단이 아니라 형식에 대한 사실이다.** 따라서 "우수한 이유", "좋은 판단" 같은 평가를 하지 않는다는 POI 원칙과 충돌하지 않는다.

> ⚠️ **주의**: 등급을 점수화하거나 사용자 간 비교 UI로 노출하지 않는다. 6.3의 배지 정책이 동일하게 적용된다.

### 3.5 Upbit Oracle 연계 (확인 필요)

GIWA 생태계에 **Upbit Oracle**이 존재한다. Oracle-anchored 등급은 이 오라클에 predicate를 대조하는 구조를 전제한다.

다만 **현재 개발자 문서가 스텁 상태로 제공 데이터 종류가 공개되어 있지 않다.** 부록 B.6 문의 목록에 포함한다.

미확인 상태에서의 대응: Oracle-anchored 등급은 **Phase 2 기능**으로 두고, MVP는 Unverified / Evidence-linked 2단계만 구현한다.

## 4. Outcome 정의

### 4.1 원칙 — 수익률이 아니다

Decision Graph에 Outcome 노드를 두면 성과가 일급 객체로 복귀한다. 여기서 정의를 잘못하면 v0.4가 의도적으로 제거한 규제 리스크가 되살아난다.

```
✗ Outcome: +12.4%
✗ Outcome: 목표 수익 달성

✓ Outcome: 선언한 조건(BTC_30D_RV > 60%)이 관측 구간 내 충족됨
✓ Outcome: 선언 이후 실행이 선언 조건과 일치함
✓ Outcome: 선언한 조건이 관측되지 않음
```

**Outcome은 "얼마 벌었나"가 아니라 "예측한 일이 일어났는가"다.** 전자는 성과 주장이고, 후자는 사실 판정이다.

### 4.2 미해결 긴장 — 명시적으로 남긴다

> 이 절은 의도적으로 "해결됨"으로 쓰지 않는다.

예측 적중 여부를 장기간 누적하면 그것은 **캘리브레이션 기록**이 되고, 사용자는 이를 "이 사람은 예측을 잘한다"로 읽는다. 즉 평가에 가까워진다.

POI는 이 긴장을 인정하고 다음으로 관리한다.

1. **적중률을 단일 수치로 표시하지 않는다** — 구간형만 사용
2. **사용자 간 비교·랭킹·리더보드를 제공하지 않는다**
3. **정렬 키로 노출하지 않는다** (API 응답 포함)
4. **미충족 결과도 동일한 시각적 비중으로 표시한다** — 성공만 강조하지 않는다
5. **법률 검토 항목으로 명시** — Phase 2 진입 전 별도 검토

### 4.3 Outcome 미발행의 의미

Decision이 t0에 이미 온체인에 존재하므로, **Outcome을 발행하지 않는 것 자체가 관측 가능한 신호**다.

```
D2 (2026-05-02 커밋, 관측 구간 90일)
    → 2026-08-01 경과
    → Outcome 미발행
    → 상태: "정산 미완료" 로 표시
```

숨길 수 없다. 이것이 사후 선택 편향을 막는 첫 번째 장치다.

## 5. Unexplained Execution — 선택 편향 탐지

> v0.5 신설.

### 5.1 남은 편향

Outcome 미발행은 막았다. 그러나 **애초에 Decision 노드를 만들지 않는 것**은 아직 막지 못했다.

```
잘 될 것 같은 판단만 기록  →  나머지는 아예 그래프에 없음
```

### 5.2 해법 — 실행 데이터와 그래프를 대조한다

Execution 데이터(도장 Verified Balance, 온체인 활동)가 존재하면, **결정 그래프로 설명되지 않는 실행을 탐지할 수 있다.**

```
관측된 실행 이벤트     :  n건
결정 노드와 연결된 실행 :  m건
                        ─────
설명되지 않은 실행      :  n − m건
```

### 5.3 신설 배지

```
✓ Fully Explained Execution
  관측 구간 내 모든 실행이 사전 결정 노드와 연결됨

△ Partially Explained
  설명되지 않은 실행 존재 (구간형: 5건 이하)
```

**이 배지는 POI에서 가장 위조하기 어려운 항목이다.** 좋은 판단만 골라 기록하면 이 배지를 잃기 때문이다.

> 심사 대응 포인트: "결정을 골라서 기록하면 되지 않나요?"에 대한 구조적 답변.

## 6. 제품 구조

```
Proof of Investing
│
├─ Decision Graph              ← 핵심 프리미티브
│  ├─ Decision (DAG 노드)
│  ├─ Reason (predicate 스키마)
│  ├─ Evidence (해시 앵커)
│  ├─ Execution (도장·온체인 대조)
│  └─ Outcome (사실 판정)
│
├─ Strategy Passport           ← MVP 핵심
│  ├─ 전략 = Decision 서브그래프
│  ├─ 버전 = 결정 노드 체인
│  └─ 운영 상태
│
├─ Trader Passport             ← Phase 2
│  ├─ Verified Address 연동
│  ├─ 활동 배지
│  └─ 공개 범위 관리
│
├─ Proof Badge                 ← EAS Attestation
│  ├─ Identity
│  ├─ Experience
│  ├─ Transparency
│  └─ Decision Integrity       ← 신설
│
└─ GIWA Layer
   ├─ Dojang (Verified Address / Verified Balance)
   ├─ EAS (발급·조회·철회)
   ├─ Upbit Oracle (Phase 2)
   ├─ up.id (프로필)
   └─ GIWA Chain (기록)
```

### 6.1 Strategy Passport = Decision 서브그래프

전략은 별도 객체가 아니다. **결정들의 연결**이다.

```
Momentum BTC v2.1
작성자: boko.up.id
루트 결정: D1 (2026-05-02)
현재 상태: 운영 중

D1  전략 생성
    Reason: [Evidence-linked]  백테스트 결과 해시 첨부

D2  손절 기준 7% → 5%                       parent: D1
    Reason: [Oracle-anchored]
            BTC_30D_RV > 60%
    Outcome: 관측 구간 내 조건 충족 ✓

D4  ETH 거래 조건 추가                       parent: D2
    Reason: [Evidence-linked]

D5  최대 포지션 비중 조정                     parent: D4
    Reason: [Unverified]
    Outcome: 미설정
```

v0.4의 Strategy Commit이 그대로 Decision Commit이 된다. **구현 범위가 늘지 않는다.**

### 6.2 Trader Passport

```
boko.up.id

✓ Verified Address                      (도장, 2026-02)
✓ 검증된 잔고 유지 6개월 이상            (도장 Verified Balance 3회)

### 6.3 배지 정책

**단일 Trust Score를 제공하지 않는다.** 복잡한 판단을 하나의 숫자로 압축하면 사용자가 이를 실력이나 미래 수익 가능성으로 오해한다.

배지 개수 역시 사실상 점수로 작동하므로 다음을 금지한다.

- 배지 개수·희소성 기준 정렬 (등록 시점순 고정)
- 사용자 간 배지 비교 UI
- 랭킹, 리더보드, "상위 n%" 표현
- API 응답에서 배지 개수를 정렬 키로 노출
- **Reason 검증 등급의 점수화·비교** (v0.5 추가)
- **Outcome 적중률의 단일 수치화·비교** (v0.5 추가)

**설계 원칙**: 사실 기반 / 조건 공개 / 발급 시점 공개 / 검증 방법 공개 / 만료일 표시 / 철회 가능 / 양도 불가 / 금전적 권리 없음

## 7. 콜드스타트 — 혼자 써도 성립하는 제품

> v0.4 대비 전면 재작성. Decision Graph가 이 문제를 크게 완화한다.

### 7.1 v0.4의 역설

- 검증의 효용이 큰 사람 = 이미 팔로워가 있는 리딩방·유튜버
- 그런데 이들은 **과거 이력 노출을 가장 피하고 싶어 한다**
- 검증에 응할 사람 = 아직 팔로워가 없어 검증의 효용이 없다

### 7.2 Decision Graph가 바꾸는 것

**의사결정 기록은 네트워크 효과가 0이어도 즉시 유용하다.**

> "내가 이걸 왜 샀지?"

모든 투자자가 스스로에게 묻고, 답하지 못하는 질문이다. 거래 기록은 있는데 판단 기록이 없기 때문이다.

따라서 진입점을 바꾼다.

```
[v0.4]  1단계: 전략 버전 관리 도구
[v0.5]  1단계: 투자 의사결정 저널   ← 훨씬 강한 개인 효용
```

### 7.3 성장 경로

```
1단계  투자 의사결정 저널
       "왜 샀는지 기록하고 나중에 확인한다"
       → 타인 불필요. 혼자 써도 완결

2단계  Pre-Commit 알리바이
       "내가 예전부터 이걸 말했다"를 미래에 증명
       → 팔로워 0명이어도 동기 존재

3단계  검증 프로필
       팔로워가 생긴 뒤 자연스럽게 필요해짐

4단계  외부 재사용
       커뮤니티·플랫폼이 POI attestation 조회
```

### 7.4 초기 타깃

| 세그먼트 | 진입 동기 | 비고 |
|---|---|---|
| **기록 습관이 있는 개인 투자자** | 판단 저널. 타인 불필요 | 가장 넓은 진입면 |
| **콘텐츠 크리에이터 (신규)** | 지금 한 말을 나중에 증명 | 팔로워 0에서도 동기 |
| **퀀트·자동매매 개인 개발자** | 이미 Git을 쓰는 층. 개념 학습 비용 0 | 초기 앰배서더 |
| **투자 커뮤니티 운영자** | 운영자가 신뢰 확보용으로 도입 → 구성원 다수 유입 | **성장 축** |

**개인 획득이 아니라 커뮤니티 단위 도입을 초기 성장 축으로 삼는다.**

증명 대상을 성과에서 의사결정으로 옮기면 투자자문업에서 **더 멀어진다.**

 이후 실행이 선언과 일치합니다"      →  사실 진술
```

후자는 상품의 가치나 투자판단에 대한 어떤 주장도 포함하지 않는다.

## 10. GIWA 기술 스택

### 10.1 도장(Dojang)

도장은 **오프체인 정보를 GIWA 체인에 온체인 attestation으로 발급하는 서비스**이며, EAS 기반이다.

| Attestation | POI 활용 |
|---|---|
| **Verified Address** | 신원 배지, 시빌 방지 |
| **Verified Balance** | **Execution 대조의 핵심 원천** |
| **Balance Root** | Verified Balance 검증 참조 |
| **Verified Code** | 계정 연결 플로우 |

```
DojangScroll : 0xd5077b67dcb56caC8b270C7788FC3E6ee03F17B9
EAS          : 0x4200000000000000000000000000000000000021
Attester ID  : keccak256("dojang.dojangattesterids.upbitkorea")
             = 0xd99b42e778498aa3c9c1f6a012359130252780511687a35982e8e52735453034
```

```solidity
function isVerified(address addr, DojangAttesterId attesterId)
    external view returns (bool);
```

**POI는 자체 검증 컨트랙트 체계를 만들지 않는다. EAS attester로 편입된다.**

이 결정의 의미:
1. 발급·철회·만료·조회를 EAS가 제공 → 개발 범위 축소
2. EAS 지원 도구가 POI 증명을 별도 개발 없이 조회 → **"재사용 가능한 증명"이 주장이 아니라 사실**
3. 다른 체인으로 이식 불가능한 설계 → GIWA-Native 정합성

### 10.2 up.id

```
형식   username.up.id     (ENS 서브도메인)
발급   Verified Address 지갑에 무료
속성   SBT — 양도·변경 불가, 지갑당 1개
호환   ENS 지원 라이브러리 전체 자동 호환
```

**지갑당 1개 + 양도 불가 + KYC 결속**이므로, 불리한 결정 그래프를 버리고 새 신원으로 재시작하는 비용이 구조적으로 높다.

### 10.3 Upbit Oracle (Phase 2)

Oracle-anchored Reason 등급의 전제. **현재 개발자 문서가 스텁 상태로 제공 데이터가 미공개다.** 부록 B.6 문의 항목.

### 10.4 보자기(Bojagi) — 의존하지 않음

보자기는 Consensus 2026에서 ZK 프라이버시 프로토콜로 발표됐으나 **개발자 문서에 페이지가 존재하지 않는다.**

- **MVP**: 구간형 증명 + 해시 커밋으로 프라이버시 확보. 보자기 없이 동작
- **Phase 4**: 공개 시 range proof·membership proof로 교체

**POI의 증명 항목은 애초에 predicate 형태로 설계되어 ZK 술어로의 전환 비용이 낮다.** 3.3의 Reason 스키마가 그대로 ZK 회로 입력이 된다.

### 13.1 Enterprise Decision Log (확인 필요)

**가설**: 자산운용사·투자자문사의 투자심의 과정은 의사결정 근거를 문서화한다. 이는 **이미 존재하고 예산이 배정된 업무**다.

POI의 Decision Graph는 이 업무를 그대로 대체하거나 보완할 수 있다.

- 심의 시점 고정
- 근거 자료 해시 앵커
- 변경 이력 불변 보존
- 외부 감사 시 독립 검증 가능

> ⚠️ **한국 규제상 구체적 문서화 의무 범위는 미확인이다.** 피치덱 반영 전 사실 확인 필요. 확인되면 "커뮤니티가 배지를 조회한다"보다 훨씬 구체적인 B2B 수요가 된다.

**원칙: 수익을 투자 손익이나 거래량에 연동하지 않는다.**

| 계정 신뢰 | 플랫폼 계정 | Verified Address (KYC 결속 SBT) |
| **선언 시점** | **기록 없음** | **온체인 고정** |
| 변경 이유 | 없거나 자유 텍스트 | **반증 가능한 predicate** |
| 선택 편향 | 통제 불가 | Outcome 미발행·Unexplained Execution으로 탐지 |
| 검증 방식 | 플랫폼 내부 DB | EAS 표준, 독립 검증 |
| 플랫폼 이동 | 불가 | 재사용 가능 |
| 투자 추천 | 빈번 | 없음 |

### 14.1 왜 GIWA인가

1. **도장 Verified Balance** — 거래소가 직접 발급하는 잔고 attestation. 다른 체인에 없음. Execution 대조의 원천
2. **Verified Address** — KYC 결속 온체인 신원. 시빌 방지 전제
3. **up.id** — 지갑당 1개, 양도 불가. 신원 세탁 방지
4. **1원 수수료** — **결정 단위 커밋이 경제적으로 성립.** L1에서는 불가능
5. **Upbit Oracle** — Reason predicate 판정 데이터 원천
6. **업비트 사용자 기반** — 검증 대상이 이미 존재

> 여섯 가지 중 하나라도 없으면 POI는 성립하지 않는다.

## 16. 예상 질문 대응

**"결국 투자자문 아닙니까?"**
POI는 종목·시점·비중·전략을 추천하지 않습니다. 사용자가 기록한 결정이 언제 만들어졌고 실제 행동과 일치하는지만 판정합니다. 판단의 우수성이나 수익 가능성을 평가하지 않습니다.

**"이유가 거짓이면 어떻게 합니까?"**
POI는 이유의 진실성을 검증하지 않습니다. **이유가 결과 이전에 고정됐고 수정되지 않았음**을 검증합니다. 또한 이유는 자유 텍스트가 아니라 반증 가능한 predicate로만 받으므로, 뭉개진 진술은 형식 단계에서 거부됩니다.

**"좋은 결정만 골라 기록하면 되지 않나요?"**
두 장치가 있습니다. ①결정은 결과 이전에 커밋되므로 Outcome 미발행이 그대로 노출됩니다. ②실행 데이터와 결정 그래프를 대조해 "설명되지 않은 실행"을 탐지합니다.

**"업비트가 Open API를 허용하지 않으면요?"**
영향 없습니다. 기본 경로는 도장이 이미 발급한 Verified Balance attestation이며, Open API는 Phase 4의 선택적 확장입니다.

**"도장이 거래내역을 검증해 줍니까?"**
도장은 Verified Address와 Verified Balance를 발급합니다. 결정 그래프와 정합성 판정은 POI가 EAS attester로서 수행합니다.

**"기존 서비스도 만들 수 있지 않나요?"**
가능합니다. 차이는 발급 주체·기준·시점·철회를 **독립적으로** 확인할 수 있고, EAS 표준이라 POI 밖에서도 읽힌다는 점입니다. 그리고 이유를 사후 수정할 수 없다는 점입니다.

**"왜 GIWA여야 합니까?"**
14.1 참조. 특히 **결정 단위 커밋은 1원 수수료가 아니면 경제적으로 성립하지 않습니다.**

**"배지가 투자 실력을 의미합니까?"**
아닙니다. 특정 사실이 확인됐다는 의미일 뿐이며, 실력이나 미래 수익을 보장하지 않습니다.

## 18. 확장 비전

POI가 판매·중개·자문을 하지 않는 검증 인프라에 머무르면 금융상품판매업자와 거리가 있다. 다음 추가 시 별도 검토 필요.

금융상품 추천 / 맞춤 추천 / 투자 성향 분석 후 상품 연결 / 금융회사 제휴 광고 / 수익률 중심 홍보 / 전략 판매·중개 / **판단 품질 평가**

### A.3 가상자산 규제

**하지 않는 행위**: 매매 / 교환 / 이전 / 자산 보관 / 매매 중개 / 출금 대행 / 공동 운용 / 자동 주문

배지는 양도 가능한 자산이 아니라 검증 상태 기록으로 설계한다.
양도 불가 / 거래 불가 / 상장 불가 / 금전적 권리 없음 / 수익 배분 없음 / 담보 기능 없음 / 만료·철회 가능

### A.4 개인정보보호

지갑 주소도 결합에 의해 개인 식별이 가능하면 개인정보로 취급될 수 있다.

**v0.5의 신규 리스크**: **Reason의 자유 텍스트가 개인 식별 정보를 포함할 수 있다.** 대응:
- Reason 원문은 온체인 기록 금지 (해시만)
- 원문 공개는 사용자 선택
- 입력 단계에서 PII 포함 경고
- predicate 부분만 온체인 판정

**기존 리스크 대응**: 경로 A(도장 Verified Balance)를 기본값으로 하면 POI가 원본 거래내역을 수집하지 않는다.

### A.5 업비트 Open API (Phase 4 조건부)
