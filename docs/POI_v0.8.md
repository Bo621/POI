# Proof of Investing

**Decision Graph — GIWA 기반 투자 의사결정 검증 인프라 v0.8**

---

## 0. 요약

| 항목 | 내용 |
|---|---|
| 프로젝트명 | Proof of Investing (POI) |
| 핵심 프리미티브 | Decision Graph |
| **MVP 정의** | **투자 의사결정이 결과 이전에 존재했고 이후 변조되지 않았음을 증명하고, 선언된 조건을 재현 가능한 방식으로 정산한다** |
| 최종 지향 | 결정과 실제 행동의 정합성 검증 (Phase 2 이후) |
| 지원 트랙 | GIWA-Native |
| 기술 의존 | GIWA Chain, EAS, 도장(Dojang), up.id |
| 사용자 자격증명 의존 | 없음 — 업비트 Open API 키 불필요 |

> 투자에서 남는 건 거래 기록이 아니라 **판단**입니다.
> 그런데 판단만 아무 데도 남지 않습니다.
> **POI는 결정을, 결과를 알기 전에 고정합니다.**

## 1. 문제

### 1.1 거래는 남고 판단은 남지 않는다

```
남는 것     :  2026-05-14  BTC 매도  0.4개
남지 않는 것 :  왜 팔았는가
              무엇을 보고 그렇게 판단했는가
              그 판단이 언제 만들어졌는가
              선언한 조건이 실제로 일어났는가
```

### 1.2 사후 서사 재구성

```
결과 확인  →  그 결과를 설명하는 판단을 사후 작성  →  "내 판단대로 됐다"
```

거짓말 탐지로 잡히지 않는다. 진술 내용이 사실이기 때문이다. 다만 **그 진술이 만들어진 시점**이 기록되지 않았을 뿐이다.

### 1.3 통찰 — GitHub는 코드 저장소가 아니다

GitHub의 가치는 저장이 아니라 `git blame`이다. 커밋은 변경분이 아니라 **"왜 바꿨는가"**의 기록이다.

```
왜 손절 기준을 7% → 5%로 바꿨는가?
```

## 2. 증명 경계

> **이 장이 문서의 중심이다.** 본문·예시·스키마·KPI는 전부 이 장에 종속된다.
> 무엇을 증명하지 *않는지*를 먼저 말하는 것이 POI의 설득 전략이다.

### 2.1 증명하는 것

| 명제 | 근거 | 강도 |
|---|---|---|
| 커밋된 결정 내용이 **시점 t0에 존재했다** | 블록 타임스탬프 | 강 |
| 커밋된 결정이 **이후 변조되지 않았다** | commitment + DAG 무결성 | 강 |
| 이 결정이 **특정 검증 지갑에 귀속된다** | 서명 + Verified Address | 강 |
| 첨부된 **근거 자료가 t0에 존재했다** | commitment | 강 |
| 선언 조건의 **정산 결과가 재현 가능하다** | 출처·버전·로직 버전 기록 | **중 — §2.2** |
| 커밋된 결정이 **정산되지 않았다** | 정산 미발행 상태 노출 (§4.3) | 중 |

### 2.2 정산의 강도 — 독립 판정이 아니다

```
MVP      POI가 외부 데이터를 가져와 POI가 판정한다.
         출처·스냅샷 시각·로직 버전을 함께 기록하므로
         제3자가 같은 절차로 결과를 재현할 수 있다.
         → 재현 가능성 (reproducibility)

Phase 2  오라클이 관측값을 독립 증명한다.
         → 독립 판정 (independent attestation)
```

**"독립"이라는 단어는 Phase 2 전용어로 예약한다.** 문서 어디에서도 MVP 정산에 사용하지 않는다.

### 2.3 증명하지 *않는* 것

| 명제 | 성격 |
|---|---|
| 이 이유가 진짜 이유였다 | **원리적 불가** — 내심의 상태는 관측 불가 |
| 이 근거가 결정을 유발했다 | **원리적 불가** — 자료의 존재 ≠ 인과 |
| 이 판단이 좋은 판단이다 | **설계상 배제** — 평가하지 않는다 |
| 모든 결정이 기록됐다 | **현 단계 미지원** — §2.4 |
| 모든 실행이 결정과 대응한다 | **현 단계 미지원** — §5 |
| 구간 내내 잔고가 유지됐다 | **현 단계 미지원** — §5.2 |

### 2.4 무결성 ≠ 완전성

| 속성 | 정의 | 현황 |
|---|---|---|
| **무결성** | 기록된 결정이 삭제·변조되지 않았다 | ✅ 증명 |
| **완전성** | 내린 결정이 전부 기록됐다 | ❌ **미증명** |

DAG는 기록된 노드의 변조를 막지만, **애초에 기록하지 않는 것**이나 **새 루트로 다시 시작하는 것**은 막지 못한다.

**Phase 2 설계 과제**: actor별 append-only 인덱스 / 활성 graph root 정의 / 분기·폐기 규칙 / 실행 데이터 대조

> 이 문서는 이 과제를 **해결됐다고 쓰지 않는다.**

### 2.5 네 가지 위조와 사정거리

| 유형 | POI |
|---|---|
| Fake Strategy — 변경 이유가 남지 않는다 | ✅ 시점 문제. 해결 |
| Fake Performance — 관측 구간을 사후에 정한다 | △ **부분** — 커밋한 결정에 한함. 애초에 커밋하지 않으면 재현됨 (§2.4) |
| Fake Identity — 불리한 결정을 기록하지 않거나 새로 시작한다 | △ **부분** — 완전성 문제 |
| Fake Reputation — 판단과 무관한 지표로 신뢰 구성 | △ 대안 제시일 뿐 |

## 3. Reason 설계

### 3.1 근본 문제

Reason은 **본질적으로 검증 불가능한 필드**다. 그리고 이유가 공개·영구 기록되는 순간, 합리적 사용자의 최적 전략은 **반증 불가능한 문장을 쓰는 것**이 된다.

```
"시장 상황 변화에 따른 리스크 조정"
"종합적 판단에 따른 비중 재조정"
```

전부 참이면서 전부 무의미하다.

### 3.2 객체 3계층

| 객체 | 저장 | DAG 노드 | predicate | 정산 | 증명하는 것 |
|---|---|---|---|---|---|
| `JOURNAL_ENTRY` | **오프체인 전용** | ✗ | — | — | **아무것도 증명하지 않음** |
| `TIMESTAMPED_NOTE` | 온체인 | ✗ (독립 노드) | — | — | 이 내용이 t0에 존재했고 변조되지 않았다 |
| `VERIFIABLE_DECISION` | 온체인 | ✓ (parent 가짐) | **필수** | 가능 | 위 + 선언 조건의 정산 |

**역할**

- `JOURNAL_ENTRY` — 지갑 없이 쓰는 진입점. 검증 대상이 아님을 UI에 상시 표시
- `TIMESTAMPED_NOTE` — **이 계층만 놓고 보면 타임스탬프 서비스와 기능이 같다.** 차별점이 아니라 온램프
- `VERIFIABLE_DECISION` — 실제 제품. predicate와 정산 규율이 붙는다

**승격 규칙**

| 경로 | t0 처리 |
|---|---|
| `JOURNAL_ENTRY` → 상위 | **승격 시점이 t0.** 소급되지 않음 |
| `TIMESTAMPED_NOTE` → `VERIFIABLE_DECISION` | **노트 내용의 t0는 보존.** predicate·정산은 승격 시점부터. 두 attestation은 링크되며 **노트 내용이 결정 내용과 동일함은 보장되지 않는다** |

> "예전부터 말했다"를 증명하려면 **그 시점에 `TIMESTAMPED_NOTE`를 남겨야 한다.** 저널만 쓰다가 나중에 승격하는 것으로는 증명되지 않는다. UI는 이 차이를 진입 시점에 명시한다.

### 3.3 predicate — 시제 분리

| 필드 | 시제 | 의미 | 필수 |
|---|---|---|---|
| `trigger_predicate` | 과거·현재 | 결정 시점에 관측한 조건 | **필수** |
| `expected_outcome_predicate` | 미래 | 앞으로 일어날 것으로 선언한 조건 | 선택 |
| `settlement_window` | — | 언제, 어떤 데이터로 판정하는가 | **`expected_outcome_predicate`가 있을 때만** |
| `execution_rule` | 조건부 | 어떤 행동이 이 결정과 일치하는가 | Phase 2 |

**`expected_outcome_predicate`를 필수로 두지 않는 이유**

> "리스크를 줄이고 싶어서 비중을 낮춘다"

이건 예측이 아니라 선호다. 미래 predicate를 강제하면 사용자가 억지 예측을 지어내고, 이는 §3.1이 막으려던 뭉개짐이 다른 형태로 돌아오는 것이다.

### 3.4 검증 등급 — 원천으로만 구분

| 등급 | 조건 | 추가로 검증되는 명제 | MVP |
|---|---|---|---|
| `SELF_DECLARED` | predicate 존재. 외부 판정 없음 | (형식 + 고정 시점만) | ✓ |
| `EVIDENCE_COMMITTED` | `evidence_commitment` 존재 | 근거 자료가 t0에 존재 | ✓ |
| `ORACLE_VERIFIED` | 관측값을 오라클이 독립 증명 | 관측값이 사실 | Phase 2 |

> ⚠️ `ORACLE_VERIFIED`가 확인하는 것은 **"이것이 실제 이유였다"가 아니라 "predicate의 관측값이 사실이었다"**이다.

**등급은 품질이 아니라 형식에 대한 사실이다.** 외부 프로필에서 점수화·비교하지 않는다 (§8.3).

### 3.5 predicate가 하는 것과 하지 못하는 것

| | |
|---|---|
| **한다** | 결정에 **최소 하나의 반증 가능한 축**을 강제한다 |
| **하지 못한다** | 자유 텍스트 본문의 뭉개짐 자체를 제거하지 못한다 |

`free_text`는 계속 허용된다. 다만 **검증 대상이 아님을 UI에 명시**하고, 원문은 온체인에 올리지 않으며 salted commitment로만 앵커한다 (부록 B.4).

## 4. Settlement (정산)

> 용어: 정산 객체를 문서 전체에서 **Settlement(정산)**로 통일한다.

### 4.1 원칙 — 수익률이 아니다

```
✗ +12.4% / 목표 수익 달성
✓ 선언 조건이 정산 구간 내 관측됨 / 관측되지 않음 / 판정 불능
```

| 구분 | 값 |
|---|---|
| Settlement attestation `result` | `OBSERVED` / `NOT_OBSERVED` / `INDETERMINATE` |
| attestation 부재 시 파생 상태 (UI 계산) | 「정산 미완료」(구간 진행 중) / 「정산 대기」(구간 종료~유예 중) / 「정산 기한 경과」(유예 경과) |

### 4.2 정산 가능한 predicate만 허용한다

`expected_outcome_predicate`는 **MVP 관측 범위 안에서 판정 가능해야 한다.**

| | 예시 | MVP |
|---|---|---|
| ✅ 시장 관측 지표 | BTC 60일 최대낙폭, 30일 실현변동성, 가격대 도달 | 가능 |
| ✅ 온체인 관측 지표 | 컨트랙트 이벤트, 온체인 잔고 변화 | 가능 |
| ❌ 전략 성과 지표 | 전략 최대낙폭, 전략 수익률, Sharpe Ratio | **불가 — 실행 데이터 필요 (§5)** |
| ❌ 개인 자산 지표 | 개인 손익, 개인 포트폴리오 낙폭 | 불가 + 규제 검토 대상 |

**metric 화이트리스트를 스키마에 선언하고, UI가 입력 단계에서 거부한다.**

### 4.3 미발행 노출 — 그리고 그 한계

커밋된 결정은 t0에 이미 온체인에 있으므로, 정산하지 않는 것이 관측된다.

**공개 범위 통제의 예외**

> `expected_outcome_predicate`를 선언한 `VERIFIABLE_DECISION`은, **정산 상태(발행 여부)를 공개 범위 설정으로 숨길 수 없다.** 결정 내용과 이유는 비공개로 둘 수 있으나 정산 상태는 항상 공개된다. 이 규칙에 동의해야 선언이 가능하다.

**한계**

- 이 규칙은 **커밋된 결정에만 적용된다.** 애초에 커밋하지 않은 결정은 여전히 탐지되지 않는다 (§2.4)
- 따라서 "숨길 수 없다"가 아니라 **"커밋한 이상 숨길 수 없다"**가 정확한 서술이다

### 4.4 미해결 긴장

예측 관측 여부를 장기 누적하면 **캘리브레이션 기록**이 되고, "이 사람은 예측을 잘한다"로 읽힌다. 즉 평가에 가까워진다.

1. 적중 관련 수치를 외부 프로필에 노출하지 않는다 (§8.3)
2. 사용자 간 비교·랭킹·리더보드 미제공
3. API 응답에서 정렬 키로 노출 금지
4. **미관측 결과도 동일한 시각적 비중으로 표시**
5. Phase 2 진입 전 법률 검토

### 4.5 재현 절차 기록

정산은 판정 결과와 함께 **출처(`source`) · 스냅샷 시각(`source_version`) · 로직 버전(`verifier_version`)**을 기록한다. 단위·소수점·타임존·경계 규칙은 부록 B.3.

## 5. Execution — 관측 한계

### 5.1 Verified Balance 정정

도장 **Verified Balance는 특정 시점의 잔고 스냅샷**이며 체결·주문 이벤트가 아니다. 따라서 다음을 알 수 없다.

- 몇 번 매수·매도했는가
- 각 실행이 언제 일어났는가
- 각 실행이 어느 Decision에 대응하는가

실행 정합성 배지는 **MVP에서 제공하지 않는다.**

### 5.2 남는 것도 과장하지 않는다

```
✗ "검증된 잔고를 6개월간 유지했다"
   → 스냅샷 사이에 0이 되었다 복구돼도 탐지되지 않는다

✓ "6개월에 걸쳐 3회 이상의 시점에서 잔고가 검증됐다"
```

**스냅샷 발급 주기가 미확인**이므로 관측 해상도를 특정할 수 없다 (부록 B.5 #2). 배지 문구는 **횟수와 기간을 함께 표기**하고 "유지"라는 단어를 쓰지 않는다.

### 5.3 Phase 2 선택지

| 경로 | 비용 |
|---|---|
| A. 온체인 거래만 Execution으로 인정 | 즉시 구현. **업비트 사용자 기반과의 연결이 약해짐** |
| B. 거래소 execution attestation 신설 | 두나무 협의 필요 (부록 B.5 #3) |
| C. 업비트 Open API | 약관 확인 필요. 전환율 저하 |

**MVP는 셋 다 채택하지 않는다.** 도입 시 배지명은 `Observable Execution Coverage`로 하고 데이터 원천과 관측 범위를 병기한다.

### 5.4 Open API 필요 여부

| 기능 | Open API | 단계 |
|---|---|---|
| 결정 커밋·불변성 증명 | 불필요 | MVP |
| Reason 형식·등급 판정 | 불필요 | MVP |
| 정산 (시장·온체인 지표) | 불필요 (공개 데이터) | MVP |
| 스냅샷 시점 잔고 배지 | 불필요 (Verified Balance) | Phase 2 |
| **실행 정합성 검증** | **경로 B 또는 C 필요** | Phase 2 |

MVP 범위에서 **사용자 자격증명 의존은 없다.** 단 GIWA Chain·EAS·도장·up.id에는 의존한다.

## 6. 제품 구조

```
Proof of Investing
│
├─ 오프체인
│  └─ JOURNAL_ENTRY            검증 대상 아님. DAG 밖
│
├─ 온체인
│  ├─ TIMESTAMPED_NOTE         독립 노드
│  ├─ VERIFIABLE_DECISION      DAG 노드 (parent 링크)
│  └─ SETTLEMENT               Decision을 참조하는 별도 노드
│
├─ Strategy Passport           MVP — Decision 서브그래프 뷰
├─ Trader Passport             Phase 2
│
└─ GIWA Layer
   ├─ EAS          레지스트리·발급·조회·철회
   ├─ Dojang       Verified Address / Verified Balance
   ├─ up.id        프로필
   └─ GIWA Chain   기록
```

```

─── 온체인 결정 그래프 ────────────────────────────────

    trigger        BTC_30D_REALIZED_VOL > 60.0%

D3  ETH 조건 추가        parent: D2   tier: SELF_DECLARED

## 7. 콜드스타트

### 7.1 역설

검증의 효용이 큰 사람은 이미 팔로워가 있는 층인데, 이들은 과거 이력 노출을 가장 피하고 싶어 한다. 검증에 응할 사람은 아직 팔로워가 없어 효용이 없다.

### 7.2 계층별 진입 비용 분할

| 단계 | 객체 | 얻는 것 | 필요한 것 |
|---|---|---|---|
| 1 | `JOURNAL_ENTRY` | **"왜 샀는지" 기록.** 혼자 써도 완결 | 없음 |
| 2 | `TIMESTAMPED_NOTE` | **"내가 이 시점에 말했다"** 증명 | 지갑 + 소액 수수료 |
| 3 | `VERIFIABLE_DECISION` | 선언 조건의 정산 이력 | + predicate 작성 |
| 4 | 외부 재사용 | 커뮤니티·플랫폼의 attestation 조회 | 팔로워 |

**핵심**: 2단계 비용이 낮기 때문에 **"나중에 증명해야 할지도 모르는" 상태에서도 미리 남길 수 있다.** 저비용 체인이 제품을 가능하게 하는 지점이다.

### 7.3 초기 타깃

| 세그먼트 | 진입 동기 |
|---|---|
| 기록 습관이 있는 개인 투자자 | 판단 저널. 타인 불필요 |
| 콘텐츠 크리에이터 (신규) | 지금 한 말을 나중에 증명 (2단계) |
| 퀀트·자동매매 개인 개발자 | 이미 Git을 쓰는 층 |
| **투자 커뮤니티 운영자** | **운영자 도입 → 구성원 다수 유입. 성장 축** |

## 8. KPI

### 8.1 미스매치 인정

| KPI | 현황 |
|---|---|
| TVL | **0** — 자산 수탁을 하지 않는다. TVL은 DeFi/RWA 트랙 지표 |
| 트랜잭션 수 | §8.2 산식 |
| 사용자 수 | 계층 진입으로 대응 (§7.2) |

### 8.2 트랜잭션 산식

**활성 사용자 1인당 연간 온체인 트랜잭션**

```
= 월 온체인 커밋 수 × 12                                  … 커밋
+ 월 온체인 커밋 수 × 12 × 선언 비율 × 정산 발행률          … 정산
+ 4                                                       … 배지 재검증(분기)
```

| 시나리오 | 월 온체인 커밋 | 선언 비율 | 정산 발행률 | 연간 |
|---|---|---|---|---|
| 보수 | 1 | 30% | 70% | **19** |
| 기준 | 3 | 50% | 70% | **53** |
| 적극 | 8 | 60% | 80% | **146** |

> "월 온체인 커밋"은 `TIMESTAMPED_NOTE` + `VERIFIABLE_DECISION`. `JOURNAL_ENTRY`는 오프체인이므로 제외.
> 정산 항은 `VERIFIABLE_DECISION`에만 적용되며, 선언 비율이 이를 반영한다.

**저비용·고빈도 체인이 결정 단위 커밋의 경제성과 시점 해상도를 만든다.** 고비용 체인에서는 커밋을 묶거나 주기를 늘려야 하므로 둘 다 나빠진다.

### 8.3 내부 지표 / 외부 노출 분리

| 지표 | 용도 | 외부 프로필 |
|---|---|---|
| 발급 attestation 총계 | 사업 KPI | 구간형 |
| 누적 `VERIFIABLE_DECISION` 수 | 사업 KPI | 구간형 |
| **정산 발행률** | 내부·GASOK 보고 | **❌ 금지** |
| **등급별 비율** | 내부 | **❌ 금지** |
| 외부 서비스의 attestation 조회 수 | 인프라 지표 | — |

**원칙: 집계 지표는 보고하되, 개인 프로필에서 비교 가능한 형태로 노출하지 않는다.**

**구간형 원칙 — 외부 노출되는 모든 개인 수치에 적용**

```
✗ 검증 가능 결정 18건       →  ✓ 10건 이상
✗ 정산 관측률 73.2%         →  ✓ 노출하지 않음
```

```

## 10. GIWA 기술 스택

### 10.1 EAS와 POI 컨트랙트의 역할

| 담당 | 주체 |
|---|---|
| attestation 레지스트리, 발급·조회·철회 | **EAS** — 재구현하지 않음 |
| 스키마 등록, 커밋 앵커링, DAG 부모 링크 무결성, 등급 판정 | **POI 앵커 컨트랙트** — 얇은 계층 |
| 정산 판정 로직 | **오프체인 verifier** — 버전 기록 |

**이식성**

EAS 표준을 쓰므로 POI attestation은 **EAS 지원 도구에서 조회 가능하다.** 이는 이식을 어렵게 만들지 않는다.

> POI가 GIWA에 결속되는 이유는 **락인이 아니라 데이터 원천(도장·up.id·Upbit Oracle)과 수수료 구조**다.

### 10.2 도장(Dojang)

| Attestation | POI 활용 | 단계 |
|---|---|---|
| Verified Address | 지갑 검증. 검증 지갑 교체 비용 상승 | MVP |
| Verified Balance | 스냅샷 시점 잔고 검증 (§5.2) | Phase 2 |
| Balance Root | Verified Balance 검증 참조 | — |
| Verified Code | 계정 연결 플로우 | — |

### 10.3 up.id

```
형식   username.up.id   (ENS 서브도메인)
발급   Verified Address 지갑에 무료
속성   SBT — 양도·변경 불가, 지갑당 1개
```

> ⚠️ 보장하는 것은 **지갑당 1개**이며 **1인당 1개가 아니다.**
> "신원 세탁 방지"가 아니라 **"검증 지갑 교체 비용을 높인다"**로 서술한다.

### 10.4 Upbit Oracle / 보자기 — 의존하지 않음

- **Upbit Oracle** — `ORACLE_VERIFIED`의 전제. 개발자 문서가 스텁 상태로 제공 데이터 미공개. MVP는 공개 데이터로 정산 (§2.2)
- **보자기(Bojagi)** — ZK 프라이버시 프로토콜로 발표됐으나 **개발자 문서에 페이지 없음.** MVP는 구간형 노출 정책 + salted commitment로 대응. predicate 형태가 **ZK 술어와 구조적으로 유사**하므로 공개 시 적용을 검토한다

### 11.1 포함 (Must) — 7/31 제출물

## 12. 경쟁 구도

| 투자 도메인 스키마 | 일부 | ✓ | ✗ 직접 만들어야 함 | ✓ |
| 성과 랭킹 | ✗ | ✓ 핵심 기능 | — | ✗ 의도적 배제 |

### 12.1 왜 GIWA인가

| 요소 | 기여 |
|---|---|
| **저비용·1초 블록** | **부담 없이 시점을 남기는 UX가 성립** (§7.2). 결정 단위 커밋의 경제성 |
| Verified Address | 검증 지갑 결속. 교체 비용 상승 |

> **"다른 체인에서는 불가능하다"고 쓰지 않는다.**
> "GIWA에서 차별화가 강화되고, 고비용 체인에서는 경제성과 시점 해상도가 나빠진다"가 방어 가능한 서술이다.

## 15. 예상 질문

**"결국 투자자문 아닙니까?"**
종목·시점·비중·전략을 추천하지 않습니다. 결정이 언제 기록됐고 선언 조건이 관측됐는지만 판정합니다.

**"이유가 거짓이면요?"**
POI는 이유의 진실성을 검증하지 않습니다. **이유가 결과 이전에 고정됐고 수정되지 않았음**을 검증합니다. predicate가 최소 하나의 반증 가능한 축을 강제하지만, **자유 텍스트의 모호함을 완전히 제거하지는 못합니다.**

**"좋은 결정만 골라 기록하면 되지 않나요?"**
**부분적으로만 막습니다.** 커밋한 결정의 정산 미발행은 공개 범위 설정으로도 숨길 수 없습니다(§4.3). 그러나 **애초에 커밋하지 않은 결정은 탐지하지 못합니다**(§2.4).

**"정산을 POI가 직접 하면 POI를 믿어야 하는 것 아닙니까?"**
맞습니다. MVP 정산은 독립 판정이 아니라 **재현 가능성**을 제공합니다. 출처·시각·로직 버전을 기록하므로 제3자가 같은 절차로 재현할 수 있습니다. 독립 판정은 오라클 연계 이후입니다.

**"타임스탬프 서비스와 뭐가 다릅니까?"**
`TIMESTAMPED_NOTE` 계층만 놓고 보면 같습니다. 그건 온램프입니다. 차별점은 **도메인 스키마 + 정산 규율 + 미발행 노출**입니다.

**"업비트 Open API를 못 쓰면요?"**
MVP 전 범위가 영향받지 않습니다. 실행 정합성 검증(Phase 2)에만 추가 데이터 원천이 필요합니다.

**"도장이 거래내역을 검증해 줍니까?"**
아닙니다. 도장은 Verified Address와 **잔고 스냅샷**을 발급합니다. 체결 이벤트는 제공하지 않습니다.

**"왜 GIWA입니까?"**
§12.1. 특히 부담 없이 시점을 남기는 UX가 저비용·고빈도 체인에서 성립합니다.

**"배지가 투자 실력을 의미합니까?"**
아닙니다. 특정 사실이 확인됐다는 의미일 뿐입니다.

- 선언한 조건이 정산 구간 내 관측됐습니다 / 관측되지 않았습니다

# 부록 B. 기술 사양

## B.1 객체 모델

```
JOURNAL_ENTRY        오프체인 전용. attestation 아님
                     ↓ 승격 시 t0 = 승격 시점

TIMESTAMPED_NOTE     poi.note.v1          revocable: false
                     ↓ 승격 시 노트 t0 보존, 링크

VERIFIABLE_DECISION  poi.decision.v1      revocable: false
        ▲
        │ decision_uid
SETTLEMENT           poi.settlement.v1    revocable: TRUE   ← 정정 위해 필수
```

> **Settlement만 `revocable: true`로 등록한다.** B.2의 정정 규칙이 EAS revoke를 사용하므로, false로 등록하면 정정이 영구 불가능해진다. **스키마 등록 시점에 굳는 값이므로 MVP 착수 전 확정 필요.**

## B.2 정정·철회 규칙

| 상황 | 처리 |
|---|---|
| decision당 유효 Settlement | **최대 1건** — `supersedes` 체인의 말단 (0건 = 미발행) |
| 중복 발행 (`supersedes: null`이 2건 이상) | 최초만 유효. 나머지 무효 |
| 정정 | 기존 Settlement를 revoke 하고 `supersedes: <이전 uid>`로 새 attestation 발행 |
| 철회 사유 | 사유 코드 필수. 정정 이력 공개 |
| Decision 자체의 정정 | **불가.** 새 Decision을 `parent`로 연결 |

> 구현은 Phase 1. MVP는 발행만 지원한다.

## B.3 판정 규칙

| 항목 | 규칙 |
|---|---|
| 직렬화 | JSON Canonicalization Scheme (RFC 8785). 해시 전 정규화 필수 |
| 수치 | 문자열 표기. 부동소수점 금지 |
| 소수점 | metric별 `decimals`를 스키마에 선언 |
| 경계 | `boundary: inclusive / exclusive` 명시 |
| 타임존 | 전부 UTC |
| 구간 | `start` inclusive, `end` exclusive |
| `source_version` | **`settlement_window` 구간 내 시각이어야 한다** |
| 유예 | **`end` 기준** `grace_period_days` 경과 후 미발행이면 「정산 기한 경과」 |

## B.4 Commitment

```
commitment = H( salt ‖ canonical_json(payload) )

salt : 128비트, 클라이언트 생성, 절대 온체인 기록 금지
H    : keccak256
공개 : (salt, payload) 제출 시 누구나 검증 가능
```

> `"손절 기준 변경"` 같은 짧은 문장은 엔트로피가 낮아 salt 없이는 사전 대입으로 복원된다.

`evidence_commitment`, `free_text_commitment`, `content_commitment` 전부 동일 규칙.
