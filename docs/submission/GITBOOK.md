# 백서(GitBook) 구성안 — 지원서 문항 10

문항 10은 **제품 아키텍처와 기술 구현을 설명하는 GitBook / 백서 / 원페이저**를 요구한다.

## 원칙 — 새로 쓰지 않는다

이미 7,900줄이 있다. **재료가 아니라 순서와 진입점이 없었을 뿐이다.**
GitBook은 기존 문서를 **재배열**하고, 중복은 링크로 잇는다.

**단, 아래 둘은 손대지 않는다.**

| | 이유 |
|---|---|
| `docs/metrics/*.md` | **파일 바이트의 해시가 온체인 `definitionHash`다.** 한 글자만 바뀌어도 검증이 깨진다 |
| `docs/POI_TechSpec_v3.md` | 명세 원본 |

GitBook에 넣을 때는 **복사하지 말고 GitHub 원본을 링크**한다.
특히 metrics 문서는 "여기 원본이 있고 이 해시가 온체인에 있다"는 식으로 링크만 건다.

## 목차안

```
POI — Proof of Insight

1. 시작하기
   1.1 무엇을 하는 제품인가          ← submission/README.md
   1.2 5분 만에 직접 확인하기         ← submission/VERIFY.md ★
   1.3 배포된 주소와 UID              ← DEPLOYMENT.md

2. 왜 이 문제인가
   2.1 판단은 남지 않는다              ← POI_v0.10 §1
   2.2 무엇이 증명되고 무엇이 안 되나   ← POI_v0.10 §2.1 명제표
   2.3 정산의 강도 — 독립 판정이 아니다 ← POI_v0.10 §2.2

3. 어떻게 막는가
   3.1 컨트랙트 불변식                 ← submission/ARCHITECTURE.md
   3.2 commitment 설계와 복사 공격     ← §4.3 + CT18
   3.3 지표 정의의 온체인 고정          ← metrics/ 링크만
   3.4 비정규 payload 차단

4. 왜 GIWA인가
   4.1 실측 비용                      ← POI_v0.10 §12.1
   4.2 고비용 체인에서 무너지는 지점    ← POI_v0.10 §12.2 ★
   4.3 생태계 편입 — EAS · 도장

5. 사용자 흐름
   5.1 화면 구조
   5.2 커밋 → 결과 등록 → 이의 → 공개
   5.3 GIWA 월렛 탑재 가능성           ← 신규 작성 필요

6. 검증하기
   6.1 온체인에서 직접                 ← VERIFY.md
   6.2 오프체인 검증기 CLI
   6.3 종료코드의 의미

7. 한계와 로드맵
   7.1 하지 못한 것                    ← submission/LIMITS.md ★
   7.2 Phase 1~3

부록
   A. 스키마 정의
   B. 불변식 전체 목록 I1~I17
   C. 테스트 구성 (407개)
```

★ 표시는 **이 백서에서 가장 읽힐 문서**다. 심사자가 1.2와 7.1을 먼저 볼 가능성이 높다.

## GitBook 설정

**GitHub 동기화를 권한다.** 저장소의 `docs/`를 그대로 연결하면
문서를 고칠 때마다 백서가 갱신되고, **문서와 코드가 어긋날 여지가 줄어든다.**

수동 복사를 하면 온체인 주소·UID·테스트 수치가 두 곳에 생기고 반드시 어긋난다.
이 저장소에서 UID가 두 번 어긋난 전례가 있다.

공개 설정: **「링크가 있는 모든 사용자가 볼 수 있음」** — 지원서 요구사항이다.
