// 01 문제

남는 건 거래 기록이지 판단이 아니다

거래는 거래소에 남고 수익률도 남는다. “왜 그렇게 판단했는가”는 아무 데도 남지 않는다.

그래서 결과를 본 뒤에 이렇게 말할 수 있다 — “나는 그럴 줄 알았다.”

// 04 강제

세 줄의 코드가 사후 서사를 막는다

if (d.windowStart < attestTime) revert WindowInPast();      // I4
if (p.time >= a.time)           revert ParentNotEarlier();  // I2
if (s.result != expect)         revert ResultMismatch();    // I17
I4관측 구간을 과거로 못 잡는다 (예상 결과를 선언한 결정에 적용)
I2부모 결정이 자식보다 엄격히 빨라야 한다
I17관측값과 모순되는 결과를 기록할 수 없다 (산술 일치만 — 관측값의 진실성은 별개)

그리고 지표 정의 문서의 바이트 해시가 온체인에 박혀 등록 즉시 frozen이다. 기준을 나중에 바꿀 수 없다.

// 05 왜 GIWA인가 ①

비용이 시점 해상도를 정한다

비용을 줄이려 커밋을 묶어도 절감은 기본가스뿐이라 약 17%에 그친다. 그리고 묶는 순간 같은 배치 안의 결정 선후 관계를 잃는다 — EAS 배치는 모든 attestation 에 같은 timestamp 를 넣기 때문이다(I2).

// 06 왜 GIWA인가 ②

새 신뢰 축을 세우지 않는다

EAS 프리디플로이스키마·발급·철회·참조를 재구현하지 않는다
도장 Verified AddressKYC 결속 온체인 신원
저비용 L2결정 단위 커밋의 경제성

그래서 앞 장의 배치 문제가 생긴다 — EAS 배치는 한 트랜잭션의 모든 attestation 에 같은 timestamp 를 넣고, I2 는 부모가 자식보다 엄격히 빨라야 한다고 요구한다.

// 10 가장 큰 반론

“좋은 판단만 골라 기록하면?”

맞다. 완전성은 보장되지 않는다. 조회된 것이 전부라는 보장도 없다.

미발행을 드러낸다선언하고 안 올리면 「기한초과」로 남는다
건수를 세지 않는다지갑 생성 비용이 0이라 개수는 언제든 부풀릴 수 있다
목록에 명시한다「조회된 것이 전부라는 보장은 없습니다」
비교·랭킹을 만들지 않는다선택 기록으로 순위를 만들면 거짓말이 된다

한 지갑 안에서의 선택적 기록은 남는다. 지금 구조로 못 푼다. Phase 2의 실행 정합성 검증이 이 문제를 좁힌다.
