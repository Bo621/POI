# Proof of Investing

**GIWA 기반 투자 활동·전략 신뢰 인프라 기획서 v0.4**

> **v0.3 → v0.4 주요 변경**
> 1. **도장(Dojang) 재해석** — 도장은 단순 주소 확인 도구가 아니라 EAS 기반 attestation 발급 서비스이며, `Verified Balance`를 제공한다. POI의 검증 레이어를 자체 컨트랙트가 아닌 **도장·EAS 표준 위에 재설계**했다.
> 2. **업비트 Open API 의존 제거** — Open API 없이 `Verified Balance` 스냅샷 누적만으로 활동 증명이 가능하다. Open API는 Phase 3 확장 옵션으로 강등.
> 3. **Pre-Commit 프로토콜을 제품 코어로 승격** — "전략을 사후에 바꾸지 않았다"를 넘어 "선언한 전략대로 실제로 거래했다"를 증명하는 구조를 명시했다.
> 4. **UP.ID 표기 수정** — `boko.giwa.id` → `boko.up.id` (ENS 서브도메인, SBT).
> 5. **보자기(Bojagi) 포지션 조정** — 개발자 문서에 아직 미공개. MVP 의존 대상이 아니라 **Phase 4 로드맵 정합성**으로 기술.
> 6. **규제 섹션 압축** — 본문 1개 장으로 축약하고 상세는 부록 A로 이동.
> 7. **KPI·콜드스타트 대응 신설** — GASOK 마일스톤(트랜잭션·사용자) 달성 논리와 초기 사용자 획득 경로를 추가.
> 8. **MVP 축소** — 5개 기능 → Strategy Passport 단일 축.

> 우리는 수익률을 증명하지 않습니다. **누가, 언제, 무엇을 선언했고, 그대로 행동했는지**를 증명합니다.

## 1. 문제 정의

투자 시장의 문제는 정보 부족이 아니라 **검증 불가능성**이다. 정보는 넘치지만 다음은 확인할 방법이 없다.

- 이 사람이 실제 투자 경험이 있는가
- 이 전략이 실제로 운영된 적이 있는가
- 백테스트가 사후에 유리하게 조정되지 않았는가
- 전략이 언제 만들어지고 어떻게 바뀌었는가
- 불리한 기록을 삭제하지 않았는가
- 계정을 새로 파서 이력을 초기화하지 않았는가

### 1.1 네 가지 위조

| 유형 | 내용 |
|---|---|
| **Fake Performance** | 백테스트 구간·조건 선택으로 성과 과장. 실운용과 시뮬레이션 구분 불가 |
| **Fake Identity** | 새 계정 생성으로 실패 이력 소거. 재등장 비용이 0 |
| **Fake Reputation** | 팔로워·리뷰·평점 구매 및 조작 |
| **Fake Strategy** | 전략 수정 시 이전 버전 소멸. 현재 버전만 공개 |

### 1.2 그리고 플랫폼 종속

기존 인증과 평판은 특정 플랫폼 안에서만 유효하다. 플랫폼이 종료되거나 계정이 삭제되면 신뢰 이력도 함께 사라진다.

### 1.3 가장 아픈 지점 — 사후 서사

현재 구조에서 가장 흔한 패턴은 단순한 거짓말이 아니라 **사후 서사 재구성**이다.

```
결과 확인 → 그 결과를 설명하는 전략을 사후 작성 → "내 전략대로 됐다"
```

이건 거짓말 탐지로 잡히지 않는다. **시점**이 기록되지 않기 때문이다.
POI가 푸는 문제는 정확히 이 시점 문제다.

## 2. 해결 구조

POI는 투자 활동과 전략 이력을 **검증 가능한 attestation**으로 전환한다.

```
사용자 활동 / 전략 선언
        ↓
검증 가능한 데이터 소스 (도장 attestation, 온체인 활동, 사용자 제출 데이터)
        ↓
POI 검증 엔진 (조건 판정, 원본 비공개)
        ↓
EAS Attestation 발급 (POI = attester)
        ↓
GIWA Chain 기록
        ↓
Trader Passport / Strategy Passport
```

핵심 원칙 세 가지.

1. **원본은 온체인에 올리지 않는다.** 조건 충족 여부와 증거 해시만 기록한다.
2. **POI는 평가하지 않는다.** 사실 판정만 한다.
3. **증명은 POI 밖에서도 읽힌다.** EAS 표준을 쓰므로 POI 서비스가 사라져도 증명은 남는다.

## 3. GIWA 기술 스택 활용 — 재설계

### 3.1 도장(Dojang)에 대한 정정

v0.3은 도장을 "Verified Address 확인 출발점"으로만 다뤘다. **이는 도장의 실제 기능을 크게 과소평가한 것이다.**

공식 문서상 도장은 **오프체인 정보를 GIWA 체인에 온체인 attestation으로 발급하는 서비스**이며, 다음 네 가지를 제공한다.

| Attestation | 내용 | POI 활용 |
|---|---|---|
| **Verified Address** | 고객확인(KYC)을 마친 지갑 주소 | 신원 배지, 시빌 방지 |
| **Verified Balance** | **특정 시점의 잔고 검증** | **활동 증명의 핵심 원천** |
| **Balance Root** | 전체 사용자 잔고의 merkle tree 요약본 | Verified Balance 검증 참조 |
| **Verified Code** | 오프체인 인증번호의 온체인 검증 | 계정 연결 플로우 |

기술 기반은 **EAS(Ethereum Attestation Service)** 이며, 다음 컨트랙트가 테스트넷에 이미 배포되어 있다.

```
DojangScroll : 0xd5077b67dcb56caC8b270C7788FC3E6ee03F17B9
EAS          : 0x4200000000000000000000000000000000000021
Attester ID  : keccak256("dojang.dojangattesterids.upbitkorea")
             = 0xd99b42e778498aa3c9c1f6a012359130252780511687a35982e8e52735453034
```

조회 인터페이스도 공개되어 있다.

```solidity
function isVerified(address addr, DojangAttesterId attesterId)
    external view returns (bool);
```

`getVerifiedAddressAttestationUid()` → EAS `getAttestation(uid)` 로 상세 조회가 가능하며, Solidity에서는 `onlyVerified` modifier로 접근 제어를 구현할 수 있다.

### 3.2 이것이 바꾸는 것

**POI는 자체 검증 컨트랙트 체계를 새로 만들지 않는다. 도장·EAS의 attester로 편입된다.**

```
[v0.3 설계]                    [v0.4 설계]
POI 자체 컨트랙트         →    EAS 스키마 + POI attester
자체 배지 포맷            →    EAS Attestation
POI 내부에서만 조회 가능  →    모든 EAS 툴링에서 조회 가능
도장은 주소 확인만        →    도장은 데이터 원천이자 표준
```

이 변경의 실질적 의미는 세 가지다.

1. **개발 범위 축소** — 발급·철회·만료·조회는 EAS가 이미 제공한다. POI는 스키마 정의와 검증 로직만 작성한다.
2. **"재사용 가능한 증명"이 주장에서 사실이 됨** — EAS를 지원하는 모든 도구가 POI 증명을 별도 개발 없이 읽는다.
3. **GIWA-Native 정합성** — 다른 체인으로 이식 불가능한 설계가 된다. "왜 GIWA인가"에 대한 답이 생긴다.

### 3.3 up.id

**표기 정정: `boko.giwa.id`는 존재하지 않는다. 올바른 형식은 `boko.up.id`이다.**

up.id의 실제 사양은 POI 설계에 유리하다.

| 사양 | POI 관점 |
|---|---|
| ENS 서브도메인 (`username.up.id`) | ENS 지원 라이브러리가 자동 호환. 개발 불필요 |
| **SBT — 양도·변경 불가** | 프로필 매매 불가 |
| **지갑당 1개** | 다중 계정 생성 억제 |
| **Verified Address 지갑에 무료 발급** | KYC와 결속. 신원 세탁 비용 상승 |

v0.3이 13.3에서 주장했던 "새 계정으로 이력을 초기화하기 어렵게 만든다"는 명제는, up.id의 실제 사양(SBT + 지갑당 1개 + KYC 결속)으로 **제품 차원에서 이미 뒷받침된다.**

### 3.4 보자기(Bojagi) — 포지션 조정

보자기는 Consensus 2026에서 **금융기관용 프라이버시 암호화 기술 / 영지식 프로토콜**로 발표됐으나, **현재 GIWA 개발자 문서에 페이지가 존재하지 않는다.**

따라서 POI는 보자기에 의존하지 않는다. 대신 다음과 같이 위치시킨다.

- **MVP (현재)**: 구간형 증명 + 해시 커밋으로 프라이버시 확보. 보자기 없이 동작한다.
- **Phase 4 (로드맵)**: 보자기 공개 시 range proof·membership proof를 그대로 교체 적용. **POI의 증명 항목은 애초에 ZK 술어(predicate) 형태로 설계되어 있어 교체 비용이 낮다.**

> 심사 대응: "보자기 나오면 뭘 하실 건가요?"에 대한 답을 미리 준비한 형태다.
> 의존하지 않으면서 정합성은 확보한다.

### 3.5 네트워크 현황

| 항목 | 값 |
|---|---|
| 메인넷 | 개발 중 (GASOK 선정 팀에 화이트리스트 프라이빗 메인넷 제공) |
| 테스트넷 | GIWA Sepolia |
| Chain ID | 91342 |

| Flashblocks RPC | `https://sepolia-rpc-flashblocks.giwa.io/` |

## 4. Pre-Commit 프로토콜 — 제품의 코어

### 4.1 v0.3의 공백

v0.3은 "실거래 연결: 확인됨"을 한 줄로 처리했다. 그러나 여기가 POI의 유일한 진짜 기술 난제이자 유일한 해자다.

전략 해시를 기록하면 **"전략을 사후에 바꾸지 않았다"**는 증명된다.
하지만 **"그 전략대로 실제로 거래했다"**는 전혀 증명되지 않는다.

후자가 없으면 POI는 타임스탬프가 붙은 GitHub에 불과하다.

### 4.2 구조

```
t0  전략 조건을 해시화하여 온체인 커밋
    → 이 시점에 아직 거래는 없다
    → 조건 원문은 비공개 유지 가능

t0 ~ t1  실제 거래 발생

t1  t0 이후의 거래 데이터 ↔ t0 커밋된 전략 조건 대조
    → 일치율 산출
    → "선언 시점 이후의 행동이 선언 내용과 일치" attestation 발급
```

핵심은 **선언이 행동보다 먼저 온체인에 박힌다는 것**이다. 그래서 사후 서사 재구성이 구조적으로 불가능해진다.

### 4.3 발급 항목

| 항목 | 예시 |
|---|---|
| 커밋 시점 | 2026-08-01T09:00:00Z (블록 타임스탬프) |
| 전략 해시 | `0x...` (원문 비공개) |
| 관측 구간 | 2026-08-01 ~ 2026-11-01 |
| 일치 판정 | 조건 충족 / 부분 충족 / 불일치 |
| 이탈 횟수 | 구간형 (예: 3회 이하) |
| 검증 로직 버전 | poi-verifier-v1.2 |

### 4.4 이 구조가 대답하는 질문

| 질문 | 답 |
|---|---|
| "성과 좋은 구간만 골라 자랑하는 것 아닌가" | 관측 구간이 선언 시점에 고정된다 |
| "실패하면 그냥 안 올리면 되지 않나" | 커밋은 t0에 이미 존재한다. 미발행 자체가 신호다 |
| "전략을 공개해야 하나" | 아니다. 해시만 커밋한다 |
| "다른 서비스도 할 수 있지 않나" | 가능하다. 단 발급자·시점·철회를 독립 검증할 수 없다 |

> **피치덱에서 이 장은 반드시 단독 슬라이드로 배치할 것.**
> "결과가 아니라 과정을 증명한다"는 메시지의 유일한 실물 구현체다.

## 5. 활동 증명 — 업비트 Open API 없이

### 5.1 v0.3 설계의 최대 리스크

v0.3은 사용자 업비트 Open API 키에 활동 검증 전체를 의존했다. 문제는 세 가지였다.

1. 거래소 Open API 약관은 통상 개인 사용 목적으로 제한되며, 제3자 서비스 제공을 제약할 수 있다
2. 사용자에게 API 키를 요구하는 것 자체가 전환율을 크게 떨어뜨린다
3. **약관 확인이 부정적으로 나오면 프로젝트 전체가 무너진다**

### 5.2 v0.4의 3단 경로

**경로 A — 도장 Verified Balance 기반 (기본값)**

도장은 **특정 시점의 잔고를 검증하는 attestation**을 발급한다. 이 attestation이 시간에 걸쳐 누적되면, 그 자체가 활동 이력이 된다.

```
2026-02  Verified Balance attestation
2026-05  Verified Balance attestation
2026-08  Verified Balance attestation
   ↓
"이 지갑은 최소 6개월간 검증된 잔고를 유지했다"
   ↓
API 키 불필요 / 원본 거래내역 불필요 / 발급 주체는 업비트
```

이 경로의 장점은 결정적이다.

- **사용자가 API 키를 넘길 필요가 없다**
- **POI가 원본 거래내역을 보관하지 않는다** — 개인정보 리스크가 구조적으로 소멸
- **검증 주체가 업비트 본인이다** — POI의 검증 신뢰도 문제도 함께 해결
- **온체인 데이터라 검증 비용이 0에 수렴한다**

**경로 B — 온체인 활동 기반 (보완)**

GIWA 및 이더리움 온체인 활동으로 산출 가능한 항목. 거래소와 무관하며 즉시 구현 가능하다.

- 지갑 최초 활동 시점
- 활동 지속 기간
- 활동 개월 수 (구간형)
- 자산군 다양성 (구간형)

**경로 C — 사용자 제출 데이터 (선택)**

사용자가 거래소에서 직접 내려받은 거래내역을 제출하는 방식. 사용자 본인의 데이터를 본인이 제출하므로 API 약관 이슈가 없다. 단, 원본 보관 리스크가 있으므로 **검증 즉시 파기하고 해시만 남긴다.**

**경로 D — 업비트 Open API 연동 (Phase 3, 조건부)**

두나무 측 서면 확인 확보 후에만 진행. **MVP 및 GASOK 제출물에는 포함하지 않는다.**

### 5.3 심사 대응

> "업비트가 API 사용을 허용하지 않으면 어떻게 됩니까?"

> **영향 없습니다.** POI의 기본 경로는 도장의 Verified Balance attestation이며, 이는 이미 온체인에 공개된 데이터입니다. 별도 권한이 필요 없습니다. Open API는 정밀도를 높이는 선택적 확장이지 전제 조건이 아닙니다.

### 6.1 Strategy Passport

전략을 문서가 아니라 **버전 관리되는 소프트웨어**로 취급한다.

```
Momentum BTC v2.1
작성자: boko.up.id
최초 등록: 2026-05-02
현재 상태: 운영 중
Pre-Commit: 활성 (관측 구간 2026-05-02 ~ )

v1.0  최초 전략 등록
v1.1  손절 기준 변경 7% → 5%   [사유 기록됨]
v2.0  ETH 거래 조건 추가        [사유 기록됨]
v2.1  최대 포지션 비중 조정     [사유 기록됨]
```

**기존 플랫폼과의 차이**

```
기존:  성과 악화 → 전략 수정 → 과거 조건 삭제 → 현재 전략만 공개
POI :  성과 악화 → 전략 수정 → 사유 기록 → 이전 버전 유지 → 전체 이력 공개
```

### 6.2 Trader Passport

```
boko.up.id

✓ Verified Address                    (도장, 2026-02 발급)
✓ 검증된 잔고 유지 6개월 이상          (도장 Verified Balance 3회 누적)
✓ 온체인 활동 3년 이상                 (온체인 검증)
✓ 전략 4개 등록                        (POI)
✓ 전략 변경 이력 전체 공개             (POI)
✓ Pre-Commit 일치 검증 2건             (POI)

최근 검증일: 2026-07-27
```

**공개하지 않는 것**: 실명, 전체 자산, 정확한 잔고, 손익, 개별 주문, API 키, 출금 주소, 거래소 회원번호

각 항목의 공개 여부는 사용자가 개별 선택한다.

### 6.3 Proof Badge 정책

**단일 Trust Score를 제공하지 않는다.** 복잡한 투자 행동을 하나의 숫자로 압축하면 사용자가 이를 실력이나 미래 수익 가능성으로 오해한다.

다만 v0.3에서 놓친 지점이 있다. **배지 개수가 사실상 점수로 작동한다.** 배지 7개와 2개는 비교된다. 따라서 다음 정책을 추가한다.

- 배지 정렬 순서를 **개수·희소성 기준으로 제공하지 않는다** (등록 시점순 고정)
- **사용자 간 배지 개수 비교 UI를 제공하지 않는다**
- 랭킹, 리더보드, "상위 n%" 표현을 제공하지 않는다
- 배지 개수를 API 응답의 정렬 키로 노출하지 않는다

**배지 설계 원칙**

사실 기반 / 조건 공개 / 발급 시점 공개 / 검증 방법 공개 / 만료일 표시 / 철회 가능 / **양도 불가** / **금전적 권리 없음**

## 7. 콜드스타트 전략

> v0.3에 없던 장. 심사에서 가장 위험한 질문이다.

### 7.1 문제

가장 아픈 질문은 이것이다. **"초기 사용자가 왜 이걸 씁니까?"**

역설이 존재한다.

- 검증의 효용이 큰 사람 = 이미 팔로워가 있는 리딩방·유튜버
- 그런데 이들은 **과거 이력 노출을 가장 피하고 싶어 한다**
- 반대로 검증에 응할 사람 = 아직 팔로워가 없어 검증의 효용이 없다

v0.3의 "권한·가시성·검증 범위로 전환" 보상은 이 역설을 풀지 못한다. **아무도 안 보는 배지를 받으려고 개인 데이터를 연결하지 않는다.**

### 7.2 해법 — 혼자 써도 쓸모 있게

POI의 첫 사용자는 **타인에게 증명하려는 사람이 아니라, 자기 전략을 관리하려는 사람**이어야 한다.

```
1단계  전략 버전 관리 도구       (혼자 써도 유용. 네트워크 효과 불필요)
  ↓
2단계  Pre-Commit 알리바이       ("내가 예전부터 이걸 말했다"를 미래에 증명)
  ↓
3단계  검증 프로필                (팔로워가 생긴 뒤 자연스럽게 필요해짐)
  ↓
4단계  외부 재사용                (커뮤니티·플랫폼이 POI 증명을 조회)
```

### 7.3 초기 타깃

| 세그먼트 | 진입 동기 | 규모 |
|---|---|---|
| **콘텐츠 크리에이터 (신규)** | 지금 한 말을 나중에 증명하고 싶다. 팔로워 0명이어도 동기가 있다 | 중 |
| **퀀트·자동매매 개인 개발자** | 전략 버전 관리가 실제 니즈. Git을 이미 쓰는 층 | 소 |
| **투자 커뮤니티·디스코드 운영자** | 개인이 아니라 **운영자가 신뢰 확보용으로 도입**. 한 번에 다수 유입 | 중 |
| **투자 동아리·트레이딩 팀** | 팀 내부 전략 이력 관리. B2B 진입점 | 소 |

**핵심 전략**: 개인 획득이 아니라 **커뮤니티 단위 도입**을 초기 성장 축으로 삼는다. 운영자 1명이 도입하면 구성원 수십 명이 따라 들어온다.

## 8. GASOK KPI 대응

> v0.3에 없던 장. 선정 이후 자금 집행과 직결된다.

### 8.1 구조적 미스매치 인정

GASOK 성과 보너스(최대 $80,000)는 트랜잭션 수, TVL, 사용자 수 기반이다. POI는 이 중 두 가지에서 구조적으로 불리하다.

| KPI | POI 현황 | 대응 |
|---|---|---|
| TVL | **0** (자산 수탁을 명시적으로 하지 않음) | 숨기지 않는다. TVL은 DeFi/RWA 트랙 지표이며 POI는 GIWA-Native / Mass Adoption 트랙 |
| 트랜잭션 수 | 배지 발급 1회성이면 매우 적음 | **반복 트랜잭션이 발생하는 설계로 전환** (아래) |
| 사용자 수 | 콜드스타트 난이도 높음 | 커뮤니티 단위 도입 (7장) |

### 8.2 반복 트랜잭션 설계

POI가 온체인 트랜잭션을 지속 발생시키는 구조는 세 가지다.

| 이벤트 | 빈도 | 근거 |
|---|---|---|
| **전략 커밋** | 전략 변경마다 | 활성 사용자는 월 1~3회 전략을 수정한다 |
| **배지 재검증** | 3개월 주기 강제 | 만료 설계가 곧 트랜잭션 설계다 |
| **Pre-Commit 정산** | 관측 구간 종료마다 | 선언 1건당 최소 2트랜잭션 (커밋 + 정산) |

```
활성 사용자 1인당 연간 온체인 트랜잭션 추정
= 전략 커밋 12~36
+ 배지 재검증 4
+ Pre-Commit 정산 4~8
= 연 20~48 트랜잭션
```

**1초 블록·1원 수수료가 이 설계를 가능하게 한다.** 이더리움 L1이었다면 재검증을 3개월마다 강제할 수 없다.

### 8.3 자체 제안 KPI

TVL 대신 다음을 마일스톤 지표로 역제안한다.

- 발급된 EAS attestation 수
- 활성 Strategy Passport 수
- 전략 커밋 수 (누적)
- Pre-Commit 정산 완료 건수
- **외부 서비스의 POI attestation 조회 수** (인프라로서의 진짜 지표)
- 배지 재검증 갱신률

## 13. 경쟁 우위

| 구분 | 기존 전략 플랫폼 | Proof of Investing |
|---|---|---|
| 계정 신뢰 | 플랫폼 계정 | Verified Address (KYC 결속 SBT) |

| **선언 시점** | **기록 없음** | **온체인 Pre-Commit** |
| 검증 방식 | 플랫폼 내부 DB | EAS 표준, 독립 검증 |
| 데이터 공개 | 상세 성과 중심 | 최소 사실 증명 |
| 플랫폼 이동 | 평판 이동 불가 | 재사용 가능 |
| 투자 추천 | 빈번 | 없음 |

### 13.1 왜 GIWA인가 (다른 체인이면 안 되는 이유)

1. **도장 Verified Balance** — 거래소가 직접 발급하는 잔고 attestation은 다른 체인에 없다
2. **Verified Address** — KYC 결속 온체인 신원. 시빌 방지의 전제
3. **up.id** — 지갑당 1개, 양도 불가. 신원 세탁 방지
4. **1원 수수료** — 반복 커밋·주기적 재검증 설계가 경제적으로 성립
5. **업비트 사용자 기반** — 검증 대상이 이미 존재하는 유일한 체인

> **이 다섯 가지 중 하나라도 없으면 POI는 성립하지 않는다.**
> GIWA-Native 트랙 지원의 근거다.

## 15. 예상 질문 대응

**"투자자문업에 해당하지 않습니까?"**
POI는 종목·시점·비중·전략을 추천하지 않습니다. 사용자 데이터에서 객관적 조건 충족 여부만 판정하며, 수익 가능성·적합성·우수성을 평가하지 않습니다.

**"업비트 거래내역을 온체인에 올립니까?"**
올리지 않습니다. 기본 경로는 도장이 이미 발급한 Verified Balance attestation이며, POI는 원본 거래내역을 보관하지도 않습니다.

**"업비트가 Open API 사용을 허용하지 않으면요?"**
영향 없습니다. Open API는 Phase 4의 선택적 확장이며 MVP 전제가 아닙니다.

**"도장이 거래내역을 검증해 줍니까?"**
도장은 Verified Address와 Verified Balance를 발급합니다. 전략 이력과 Pre-Commit 일치 검증은 POI가 EAS attester로서 수행합니다.

**"기존 서비스도 배지를 만들 수 있지 않나요?"**
가능합니다. 차이는 발급 주체·기준·시점·철회 상태를 **독립적으로** 확인할 수 있고, EAS 표준이라 POI 밖에서도 읽힌다는 점입니다.

**"왜 수익률을 공개하지 않습니까?"**
수익률은 기간과 조건에 따라 달라지고 투자 권유로 오해될 수 있습니다. POI는 미래를 예측하는 서비스가 아니라 과거의 진위를 검증하는 서비스입니다.

**"배지가 높은 투자 실력을 의미합니까?"**
아닙니다. 특정 사실이 확인됐다는 의미일 뿐이며, 실력이나 미래 수익을 보장하지 않습니다.

**"왜 GIWA여야 합니까?"**
13.1 참조. 도장 Verified Balance, KYC 결속 Verified Address, 지갑당 1개 up.id, 1원 수수료, 업비트 사용자 기반 — 다섯 가지가 모두 있는 체인이 GIWA뿐입니다.

### A.1 자본시장법

금융투자상품의 가치 또는 투자판단에 관한 추천·자문을 제공하면 투자자문업 이슈가 발생할 수 있다. 특히 주식·ETF·증권형 토큰까지 확장 시 적용 가능성이 커진다.

**초기 범위를 가상자산 투자 활동 검증으로 한정한다.**

**허용 표현**
- 365일 이상 활동이 확인됐습니다
- 검증된 잔고를 6개월간 유지했습니다
- 전략은 2026년 5월 2일 최초 등록됐습니다
- 등록 이후 4회의 변경 이력이 있습니다
- 선언 시점 이후 행동이 선언 내용과 일치합니다

**금지 표현**
- 우수 투자자입니다
- 수익 가능성이 높은 전략입니다
- 초보자에게 적합합니다
- 안전한 전략입니다
- 지금 따라 하면 좋습니다

### A.2 금융소비자보호

POI가 판매·중개·자문을 하지 않는 검증 인프라에 머무르면 금융상품판매업자와 거리가 있다. 다음 기능 추가 시 별도 검토가 필요하다.

금융상품 추천 / 전략 맞춤 추천 / 투자 성향 분석 후 상품 연결 / 금융회사 제휴 광고 / 수익률 중심 홍보 / 전략 판매·중개

### A.3 가상자산 규제

**하지 않는 행위**: 매매 / 교환 / 이전 / 자산 보관 / 매매 중개 / 출금 대행 / 공동 운용 / 자동 주문

이를 통해 가상자산사업자 해당 가능성을 낮춘다. 배지는 양도 가능한 자산이 아니라 검증 상태 기록으로 설계한다.

### A.4 개인정보보호

지갑 주소도 다른 정보와 결합해 개인을 식별할 수 있다면 개인정보로 취급될 수 있다.

**v0.4의 구조적 개선**: 경로 A(Verified Balance)를 기본값으로 하면 **POI가 원본 거래내역을 애초에 수집하지 않는다.** v0.3의 최대 운영 리스크가 설계 차원에서 제거된다.

경로 C(사용자 제출) 사용 시에만 원본이 일시적으로 존재하며, 이 경우:
- 암호화 저장
- 검증 완료 즉시 파기
- 해시만 보존
- 접근 로그 관리
