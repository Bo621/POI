# C4-R2 만료된 `verifiedAddressUID` 거부

## 왜

GIWA Sepolia의 Dojang 검증 attestation은 **`expirationTime`이 0이 아니다** — 발행 30일 뒤 만료된다
(실측: `0x072d75e1…` 스키마, `time=1784985117` / `expirationTime=1787577117`).

지금 `POIDecisionResolver._checkVerifiedAddress`는 UID가 **존재하고 recipient가 발행자 본인인지**만
본다. 만료 검사가 없다. 그래서 **이미 만료된 검증 UID로도 커밋할 수 있다.**

B4가 주장하려는 것은 "**커밋 시점의** 검증 상태 스냅샷"이다. 만료된 것을 받으면
그 시점에 검증되지 않은 지갑이 검증된 것처럼 기록된다 — 주장 자체가 거짓이 된다.

배포 후에는 리졸버를 바꿀 수 없다. 지금이 마지막 시점이다.

## 파일

- 수정: `contracts/src/POIDecisionResolver.sol` — `_checkVerifiedAddress`와 에러 선언만
- 수정: `contracts/test/POIDecisionResolver.t.sol` — 테스트 추가
- 수정: `contracts/test/fork/POIFullStack.fork.t.sol` — 포크 테스트 추가
- **그 외 파일 수정 금지.**

## 컨트랙트 변경

`POIDecisionResolver`에 에러를 추가한다:

```solidity
error VerifiedAddressExpired();
error VerifiedAddressRevoked();
```

`_checkVerifiedAddress(bytes32 verifiedUID, address attester)`를 고친다.
**시그니처를 바꿔야 한다** — 커밋 시각이 필요하다:

```solidity
function _checkVerifiedAddress(bytes32 verifiedUID, address attester, uint64 attestTime) private view
```

호출부(`onAttest`)에서 `a.time`을 넘긴다.

검사 순서:

```
1. verifiedUID == 0        → 그대로 통과 (미검증 지갑 허용. 이 규칙은 바꾸지 않는다)
2. v.uid == 0              → BadVerifiedUID (기존)
3. v.recipient != attester → BadVerifiedUID (기존)
4. v.revocationTime != 0   → VerifiedAddressRevoked        ← 신설
5. v.expirationTime != 0 && v.expirationTime <= attestTime → VerifiedAddressExpired   ← 신설
```

- **`expirationTime == 0`은 통과시킨다.** 만료 없는 검증도 유효하다.
- 비교는 `<=`다. 만료 시각 **정각**은 이미 만료로 본다 (EAS도 `expirationTime`을
  "이 시각 이후 무효"로 다룬다. 경계에서 관대하면 주장이 약해진다).
- `attestTime`은 `a.time` — 커밋 시점이다. `block.timestamp`를 쓰지 말 것.

주석에 이유를 남긴다: Dojang 검증은 30일 만료다. 만료된 스냅샷을 받으면
"커밋 시점에 검증됐다"는 주장이 거짓이 된다(B4).

## 단위 테스트 — `contracts/test/POIDecisionResolver.t.sol`

기존 `_store` 헬퍼는 `expirationTime`·`revocationTime`을 0으로 고정한다.
**기존 헬퍼를 바꾸지 말고** 검증용 헬퍼를 새로 하나 만든다:

```solidity
function _storeVerified(bytes32 uid, address recipient, uint64 expirationTime, uint64 revocationTime)
    internal returns (bytes32)
```

`recipient`가 채워진 attestation을 저장한다 (기존 `_store`는 `recipient`가 0이라 쓸 수 없다).

| # | 테스트 이름 | 확인 |
|---|---|---|
| 1 | `test_Attest_AcceptsNonExpiringVerifiedUID` | `expirationTime = 0` → 통과 |
| 2 | `test_Attest_AcceptsVerifiedUIDExpiringLater` | `expirationTime = NOW + 1 days` → 통과 |
| 3 | `test_Attest_RevertsOnExpiredVerifiedUID` | `expirationTime = NOW - 1` → `VerifiedAddressExpired` |
| 4 | `test_Attest_RevertsOnVerifiedUIDExpiringExactlyNow` | `expirationTime = NOW` → `VerifiedAddressExpired` (경계) |
| 5 | `test_Attest_RevertsOnRevokedVerifiedUID` | `revocationTime != 0` → `VerifiedAddressRevoked` |
| 6 | `test_Attest_StillAllowsZeroVerifiedUID` | `verifiedAddressUID = 0` → 통과 (미검증 지갑 허용이 깨지지 않았는지) |

기존 `BadVerifiedUID` 테스트가 그대로 통과해야 한다.

## 포크 테스트 — `contracts/test/fork/POIFullStack.fork.t.sol`

실제 EAS에 **만료가 붙은 attestation을 발행**해 그것을 `verifiedAddressUID`로 쓰면
결정 발행이 막히는지 확인한다.

| 테스트 이름 | 내용 |
|---|---|
| `test_Fork_CT20_ExpiredVerifiedAddress` | 임의 스키마로 `recipient = ALICE`, `expirationTime = now + 1시간`인 attestation 발행 → `vm.warp(now + 2시간)` → 그 UID로 결정 발행 시 `VerifiedAddressExpired` |

`EASForkBase._attest`는 `expirationTime = 0` 고정이므로, 이 테스트는 `eas.attest`를
직접 호출해 만료를 넣는다 (기존 `test_Fork_CT03_ExpirationTime`과 같은 방식).

`vm.warp` 후에도 결정의 `windowStart`가 발행 시점보다 미래여야 한다(I4) — 시간 계산에 주의할 것.

## 하지 말 것

- 미검증 지갑(`verifiedAddressUID == 0`) 허용 규칙을 바꾸지 말 것.
- 다른 리졸버를 손대지 말 것.
- 기존 테스트 헬퍼의 시그니처를 바꾸지 말 것 (다른 테스트가 깨진다).
- 명세 문서(`docs/POI_*.md`) 읽지 말 것.

## 리뷰 대응 R1 — X7 매핑 추가

X7의 커버리지 테스트(`core/test/errors.test.ts`)가 설계대로 깨졌다:
`contracts/src`에 `VerifiedAddressExpired`·`VerifiedAddressRevoked`가 생겼는데
`core/src/errors.ts`에 한국어 메시지가 없다.

`core/src/errors.ts`의 `RESOLVER_ERROR_MESSAGES`에 두 항목만 추가한다.
**다른 항목은 건드리지 말 것.**

기존 메시지들과 같은 밀도로, 사용자가 다음에 무엇을 할지 알 수 있게 쓴다:

| 이름 | 메시지 |
|---|---|
| `VerifiedAddressExpired` | 검증 상태의 유효기간이 지났습니다. 지갑을 다시 검증한 뒤 커밋해 주세요. |
| `VerifiedAddressRevoked` | 검증이 철회된 지갑입니다. 검증 없이 진행하려면 검증 UID를 비워 주세요. |

검증: `cd core && npm test` → 54/54
