# V4 — reveal 검증 CLI

`(salt, payload)` → `C` 재계산 → 온체인 commitment와 대조.
화면의 `공개` 절이 하는 일을 터미널로 옮긴다. 심사자가 브라우저 없이 검증할 수 있어야 한다.

## 절대 조건 — attester는 입력이 아니다

**`--attester` 같은 플래그를 만들지 말 것.**

commitment 프리이미지에 attester가 들어간다(`core/src/commitment.ts`).
attester를 사용자가 넣을 수 있으면, B가 A의 commitment를 그대로 복사해 커밋해 놓고
검증할 때만 A의 주소를 타이핑해서 **일치**를 받아낼 수 있다. CT18이 무력화된다.

attester와 commitment는 **둘 다 온체인 attestation에서 읽는다.** 사용자가 넣는 것은
`(salt, payload, tag)`뿐이다. `web/src/reveal.tsx`가 같은 이유로 attester를
`<output>`으로 두고 있다 — 그 결정을 그대로 따른다.

## 새 실행 파일

`package.json`의 `bin`에 추가한다. `poi-verify`의 서브커맨드로 만들지 않는다 —
인자 파서가 서로 다르고, 섞으면 둘 다 읽기 어려워진다.

```
"poi-reveal": "./src/reveal-cli.ts"
```

```
사용법: poi-reveal <decisionUID> --salt <hex> --payload <파일|-> [--tag TAG] [--rpc <url>] [--json]

  --salt      16바이트 hex (0x + 32자)
  --payload   JSON 파일 경로. `-`이면 stdin
  --tag       DECISION(기본) | TRIGGER | EVIDENCE | REASON
  --rpc       기본값은 POI_RPC_URL 환경변수
  --json      리포트를 JSON으로
```

환경변수는 `poi-verify`와 동일하게 `POI_EAS_ADDRESS`를 요구한다.
`POI_SETTLEMENT_RESOLVER_ADDRESS`·`POI_METRIC_REGISTRY_ADDRESS`는 **요구하지 않는다** —
reveal 검증에 쓰지 않는데 요구하면 심사자가 쓸데없이 막힌다.
따라서 `requiredAddress`를 재사용하되 EAS 주소만 검사한다.

## 종료 코드 — V2의 규율을 따른다

```
0  MATCH            재계산한 C가 온체인 commitment와 같다
1  MISMATCH         다르다 (salt·payload가 틀렸거나 타인의 commitment 복사본)
2  조회·입력 실패    RPC 오류, UID 없음, salt 형식 오류, payload JSON 파싱 실패
3  NOT_COMMITTED    해당 tag의 commitment가 0x00…00 — 커밋한 적이 없어 검증할 대상이 없다
```

3이 필요한 이유는 V2와 같다. `0`으로 두면 "검증됐다"와 구별되지 않고,
`1`로 묶으면 "틀렸다"와 뭉개진다. **커밋하지 않은 것은 틀린 것이 아니다.**

## 구현

### 1. `src/reader.ts` — 나머지 commitment 3종 노출

`OnChainDecision`에 이미 `evidenceCommitment`가 있다. 같은 decode 경로에서
나머지를 함께 꺼낸다. **새 `ChainReader` 메서드를 만들지 말 것** — decode가 두 곳으로 갈라진다.

```ts
decisionCommitment: decoded[3],
triggerCommitment:  decoded[4],
// evidenceCommitment: decoded[5]  (이미 있음)
reasonCommitment:   decoded[6],
```

`OnChainDecision` 인터페이스에도 세 필드를 추가한다.
인덱스는 `web/src/read.ts`의 `commitmentIndex`와 같아야 한다 — 다르면 한쪽이 틀린 것이다.

### 2. `src/reveal.ts` — 순수 함수

```ts
export const REVEAL = {MATCH: "MATCH", MISMATCH: "MISMATCH", NOT_COMMITTED: "NOT_COMMITTED"} as const;

export interface RevealReport {
    verdict: (typeof REVEAL)[keyof typeof REVEAL];
    tag: DecisionCommitTag;
    decisionUID: Hex;
    attester: Hex;        // 온체인에서 읽은 값 — 리포트에 반드시 남긴다
    onChainCommitment: Hex;
    computedCommitment: Hex | undefined;   // NOT_COMMITTED이면 undefined
    chainId: number;
}
```

- `@poi/core`의 `commitment` / `verifyReveal`을 **재사용한다.** 두 벌을 만들지 않는다(V1 원칙).
- `chainId`는 RPC에서 읽는다. 하드코딩하지 않는다 — commitment 프리이미지에 들어가는 값이다.
- commitment가 `0x00…00`이면 `NOT_COMMITTED`를 반환하고 재계산하지 않는다.
- 네트워크를 타지 않는 순수 함수로 만들고, CLI가 조회 결과를 넣어준다. `verify.ts`와 같은 구조다.

### 3. `src/reveal-cli.ts`

`cli.ts`의 인자 파싱·에러 처리 형태를 그대로 따른다(`main(argv)` export + `main().then(exit, exit 2)`).

`--payload -`는 stdin 전체를 읽는다. 파일 경로면 `node:fs/promises`의 `readFile`.

기본 출력:
```
판정: MATCH
tag: DECISION
attester: 0x…          ← 온체인에서 읽음
온체인 commitment: 0x…
재계산 commitment: 0x…
```

MISMATCH일 때 **"salt나 payload가 다르거나 다른 사람의 commitment 복사본일 수 있습니다"** 를
한 줄 덧붙인다. 화면과 같은 문구다.

## 테스트 — `test/reveal.test.ts`

`FakeReader`를 재사용한다. 단 **`decision()` fixture의 `attester`가 `uid("a")`(32바이트)라
commitment 계산에 쓸 수 없다.** reveal 테스트용으로 20바이트 주소를 쓰는 fixture를 따로 만든다.
기존 fixture는 건드리지 말 것 — 다른 테스트가 의존한다.

| # | 케이스 | 기대 |
|---|---|---|
| 1 | 올바른 (salt, payload) | `MATCH` · exit 0 |
| 2 | salt 1비트 변경 | `MISMATCH` · exit 1 |
| 3 | payload 값 변경 | `MISMATCH` · exit 1 |
| 4 | payload 키 순서만 바꿈 | **`MATCH`** — JCS 정규화가 흡수한다 |
| 5 | **CT18** — A의 (salt, payload)를 B가 복사한 결정에 대조 | `MISMATCH` · exit 1 |
| 6 | 해당 tag commitment가 0x00…00 | `NOT_COMMITTED` · exit 3 |
| 7 | TRIGGER·EVIDENCE·REASON 각 tag가 올바른 인덱스를 읽는다 | 각각 `MATCH` |
| 8 | salt 형식 오류 (15바이트, 접두사 없음) | throw · exit 2 |
| 9 | payload가 JSON이 아님 | throw · exit 2 |
| 10 | 없는 decisionUID | throw · exit 2 |
| 11 | 결정 스키마가 아닌 attestation | throw · exit 2 |

**5번이 이 항목의 존재 이유다.** 다른 걸 다 통과해도 5번이 실패하면 아무 의미가 없다.
테스트는 A의 주소로 C를 만들고, 그 C를 attester가 B인 결정에 넣은 뒤,
A의 (salt, payload)로 검증해서 **불일치**가 나오는지 본다.
