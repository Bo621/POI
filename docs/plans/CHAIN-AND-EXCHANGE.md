# 체인 선택과 거래소 연결 아키텍처

> GIWA 는 GASOK 공모를 위한 선택이었습니다. 재단 지원은 그 제약이 없으므로
> **처음부터 다시 고릅니다.** 그리고 지금 비어 있는 「③ 한 것」 칸을 어떻게 채울지
> 설계합니다.
>
> 이 문서의 사실은 전부 검색으로 확인했습니다. 확인하지 못한 것은 그렇게 적었습니다.

---

## 요약 — 두 가지가 바뀝니다

```
① 체인      GIWA → Base
            Coinbase Verifications 가 「도장」을 대체합니다. 더 강합니다.

② 실행 증명  「거래소가 열어 주기를 기다린다」 → 「오늘 열 수 있다」
            온체인 DEX 는 허락이 필요 없습니다.
```

**②가 더 중요합니다.** 지금 사업계획서는 「③ 한 것」 칸을 `✕ 비어 있다`로 두고
「거래소 체결 내역 접근이 필요하다」고 적습니다. **그게 틀렸습니다** —
온체인 파생 거래소에서는 체결이 이미 공개돼 있습니다.

# Ⅰ. 체인 선택

## POI 가 체인에 요구하는 것

| | 왜 |
|---|---|
| **EAS 네이티브** | POI 전체가 EAS 위에 있습니다. 없는 체인으로 가면 몇 달을 다시 씁니다 |
| **신원 도장** | 「누가 말했는가」가 붙어야 합니다. GIWA 도장의 대체재가 필요합니다 |
| **낮은 기록 비용** | 판단을 자주 남겨야 의미가 생깁니다 |
| **타겟이 있는 곳** | 영어권 크립토 KOL |
| **지속성** | 「증명」이 상품인데 체인이 사라지면 증명도 사라집니다 |

## 후보 비교

| | EAS | 신원 도장 | 사람 |
|---|---|---|---|
| **GIWA** | ✅ predeploy | 도장 — **파우셋 발급분만 검증했고 KYC 경로는 미검증** | 국내 |
| **Base** | ✅ predeploy (OP Stack) | ✅ **Coinbase Verifications** | 영어권 · Farcaster · Zora |
| Optimism | ✅ predeploy | ✕ (Attestation Station 은 유산) | 개발자 중심 |
| Arbitrum | ✅ 배포됨 | ✕ | 트레이더 |
| Solana | ✕ EAS 없음 | — | 큼 (건당 $0.0006) |

## 권고 — Base

**세 가지 이유입니다.**

**① 코드가 거의 그대로 동작합니다.**
Base 는 OP Stack 이라 **EAS 가 GIWA 와 똑같이 predeploy** 로 들어 있습니다.
POI 의 「스키마와 발급자를 둘 다 검증하고 통과시킨다」는 패턴이 그대로 성립합니다.
컨트랙트 재배포와 스키마 재등록이 필요하지만 **설계를 다시 하지는 않습니다.**

> GIWA 를 고른 것이 낭비가 아니었다는 뜻이기도 합니다. 같은 OP Stack 이라
> 그때 만든 것이 그대로 옮겨집니다.

**② 「도장」 문제가 오히려 해결됩니다.**

```
Coinbase Verifications
  Base 위에 EAS 로 발행 · ENS  verifications.coinbase.eth
  Verified Account   Coinbase 거래 계정 보유 (KYC 기반)
  Verified Country   ISO 3166-1 국가 코드
```

지금 POI 의 도장 서술은 정직하지만 약합니다 — **파우셋 발급분만 받아 봤고
KYC 경로는 검증하지 못했다**고 적어 두었습니다. Coinbase Verifications 는
**실제 KYC 를 거친 전 세계 사용자** 기반입니다.

**Verified Country 는 규제 대응에도 쓸 수 있습니다.** 국가별로 노출 범위를
다르게 가져가야 할 때 온체인에서 판정할 수 있습니다.

**③ 타겟이 그곳에 있습니다.** 영어권 크립토 KOL·크리에이터 문화가 Base 에 모여 있습니다.

## 확인하지 못한 것

- **Base 의 커밋 1건 실측 비용.** GIWA 1.21원은 영수증 기준 실측입니다.
  Base 도 같은 방식으로 재보아야 합니다. **옮기기 전에 반드시 실측할 것.**
- Solana Attestation Service 의 현황 — 검색으로 확인되지 않았습니다.

# Ⅱ. 거래소 연결 아키텍처 — 「③ 한 것」

## 지금 사업계획서가 말하는 것 — 고쳐야 합니다

> ③ 한 것 · 말한 대로 실제로 거래했다 · **✕ 비어 있다** · 거래소 체결 내역 접근

**이 서술은 CEX 만 생각한 것입니다.** 온체인 파생 거래소에서는 모든 체결이
이미 공개돼 있고, **누구의 허락도 필요 없습니다.**

## 3계층 설계

```
Tier 1  온체인 DEX      오늘 가능 · 허락 불필요 · 완전성이 가장 높음
Tier 2  CEX + zkTLS     사용자가 스스로 증명 · API 키를 넘기지 않음
Tier 3  거래소 서명      가장 강함 · 협상 필요
```

---

### Tier 1 — 온체인 DEX (지금 바로)

**Hyperliquid** 는 모든 체결·포지션·지갑 상호작용이 온체인에 기록되고,
공개 REST·WebSocket API 로 **지갑 주소만 넣으면** 체결 이력을 조회할 수 있습니다.

```
t0  결정 커밋
    · 판단 (지금과 동일)
    · 실행 바인딩 — 이 판단을 실행할 지갑 주소
    · 지갑 소유 증명 — 해당 지갑의 서명

t1  구간 종료
    · 공개 API 로 그 지갑의 해당 구간 체결을 수집
    · 방향 · 수량 구간 · 평균가로 요약

t2  대조
    · 선언한 방향과 실제 체결 방향이 일치하는가
    · 컨트랙트가 술어로 판정 — 지금의 정산 산술과 같은 구조
```

**여기가 결정적입니다 — 완전성이 실제로 좁아집니다.**

지금 POI 의 가장 큰 반론은 「**좋은 판단만 골라 기록하면?**」입니다.
바인딩된 지갑에서는 **그 지갑의 모든 거래가 보입니다.** 그래서

> 거래는 있는데 결정이 없으면, **그것도 드러납니다.**

완전성을 완전히 풀지는 못합니다 — 다른 지갑을 쓰면 됩니다.
하지만 **「선언한 지갑 안에서의 완전성」은 증명됩니다.** 지금은 그것조차 없습니다.

**제3자가 재현할 수 있습니다.** 같은 공개 API 로 같은 값을 다시 구합니다.
POI 서버를 믿을 필요가 없습니다 — 지금 관측값을 다루는 방식과 같습니다.

| 후보 | 상태 |
|---|---|
| **Hyperliquid** | 온체인 체결 · 공개 API · 지갑 단위 조회 — **검색으로 확인** |
| GMX · dYdX · Jupiter | 같은 성격으로 보이나 **개별 확인 필요** |

---

### Tier 2 — CEX + zkTLS (권한 없이)

**서브파티 접근 금지 문제를 우회하는 방법이 있습니다.**

지금까지의 전제는 「POI 가 거래소 API 에 접근한다」였고, 국내 거래소는 약관이
이를 금지합니다. **zkTLS 는 구조가 다릅니다** — 사용자가 **자기 브라우저 세션에서**
증명을 만들고, POI 는 그 증명만 받습니다.

```
사용자 → 거래소에 로그인 (평소대로)
       → zkTLS 로 「이 구간에 이 방향으로 체결이 있었다」는 증명 생성
       → 증명만 POI 에 제출

POI 는 API 키도, 비밀번호도, 원장 전체도 받지 않습니다.
```

zkPass 는 **Binance 를 명시적으로 지원 대상에 넣고 있습니다.**
Reclaim Protocol 도 같은 계열(프록시 모델)입니다.

> ⚠️ **법률 검토가 필요합니다.** 「서브파티 API 접근 금지」는 피하지만,
> 거래소 약관의 **자동화·스크래핑 조항**에 걸리는지는 확인하지 못했습니다.
> 국가별로도 다릅니다. **확인 전에는 Tier 1 만 이야기합니다.**

---

### Tier 3 — 거래소 서명 (장기)

거래소가 체결 요약에 직접 서명해 주는 형태입니다. 가장 강하지만 협상이 필요하고,
**Tier 1·2 로 사용자가 모인 뒤에야 협상 카드가 생깁니다.** 순서가 뒤바뀌면 안 됩니다.

---

## 무엇을 온체인에 올리고 무엇을 올리지 않나

| 올린다 | 올리지 않는다 |
|---|---|
| 실행 바인딩 (지갑 주소 또는 계정 식별 해시) | 원장 전체 |
| 체결 요약의 해시 | 보유 수량 · 잔고 |
| 술어 판정 결과 (선언 방향 = 실제 방향) | 개별 체결가 |

**잔고를 밝히지 않고 「했다」만 증명합니다.** 이 원칙은 지금 POI 가
관측값을 다루는 방식과 같습니다.
